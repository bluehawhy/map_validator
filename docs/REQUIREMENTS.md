# 요구사항 및 판정 기준 — map_validator

> 업데이트: 2026-11-04  
> 기준: [컨셉](PROJECT_CONCEPT.md) · [4단계 디자인](INTERSECTION_REVIEW_DESIGN.md) · [개발 지침](PROJECT_GUIDELINES.md)  
> **현장 테스트를 하나씩 진행하면서 새로운 기준·예외 사례를 계속 추가할 수 있다.** 변경이 컨셉에 영향을 주면 컨셉 문서도 함께 수정한다.

## 1. 목적·검수 단위

- 현재 클릭 선택한 **Polygon/Link 검수 ID**별로 입력툴(HD_3D Tool) 기대 정보와 로드뷰(NLadybugSv) 실제 관측 정보를 비교한다.
- **사용자가 직접 시점·위치를 맞추고 촬영 버튼을 누른다.** 프로그램은 창/카메라를 자동 조작하지 않는다.
- 네 촬영 타입은 **진입 전(`before`), 좌(`after_left`), 직(`after_straight`), 우(`after_right`)**. 순서는 진입 전 → 좌 → 직 → 우.
- **도로가 없는 방향도 반드시 사진을 찍는다.** 촬영하지 않은 상태와 도로가 실제 없는 상태는 다르다.
- **도로 없음은 사용자가 촬영을 건너뛰며 수동 표시하는 상태가 아니다.** 실제 사진에서 도로·건물 등 비도로 영역의 후보를 검출하여 입력툴 예상 방향과 비교한다.
- 입력툴에 해당 방향 도로가 있는데 실제 촬영 방향에 **건물이 뚜렷하고 도로가 거의 없다면 불일치 의심**으로 표시한다. **사진에 건물이 포함됐다는 사실만으로** 도로가 없다고 단정하지 않는다.
- 결과는 후보·증거·보류 사유를 함께 제공하며 최종 검수 판단은 사용자만 한다.

## 2. 촬영·보관 정책

- 각 단계 버튼은 HD_3D Tool과 NLadybugSv를 **WGC로 각각 한 장씩 캡처**한다.
- **PrintWindow 금지**, 창 활성화/이동/크기 변경/자동 복원/Zoom/로드뷰 키 입력 없이 현재 화면만 읽는다.
- 동일 단계 재촬영 시 **원본 이력을 보존**하고 촬영 버전과 최신 이미지 경로를 기록한다.
- 저장 위치: `output.directory/<검수 ID>/captures/<stage>/`, 메타데이터 `staged_capture.json`.
- 실패·한쪽 파일 누락·미촬영은 촬영 완료로 간주하지 않는다.
- `config.yaml`에는 개인 창 제목·저장 경로 설정만 둔다. **선택한 Polygon/Link ID는 저장하지 않는다.**
- 실무 사진, 개인정보, 검수 식별정보, 로컬 설정 및 결과 데이터는 GitHub에 올리지 않는다.

## 3. 진입 전 검수 항목

| 항목 코드 | 입력툴에서 기대하는 정보 | 로드뷰에서 확인할 정보 |
|---|---|---|
| `stop_line` | 시안색 **가로 정지선** 유무 | 실제 정지선 유무 |
| `entry_lane_count` | 교차로 진입 전 차로 수 | 실제 진입 차로 수 |
| `lane_arrows` | 각 차로의 좌/직/우 및 좌직/직우 등 조합 | 실제 노면 방향 화살표 |
| `colored_guidance` | 컬러유도선 유무·색·개수 | 실제 컬러유도선 유무·색·개수 |

시안색 **진입 선형**은 시안색 **가로 정지선**과 구분한다. 입력툴의 정지선 판정 기준은 **무조건 시안색 가로줄 존재 여부**다. 로드뷰의 가로 흰색 노면표시는 **횡단보도가 아닌 실제 단독 정지선**인지 구분한다.

### 진입 전 정지선 PASS / FAIL / REVIEW 규칙 (2026-11-04 확정)

- **입력툴**: 검은 도면 화면의 시안색 가로줄을 찾는다. 감지되면 정지선 있음(`true`), 도면이 정상 식별되는데 가로줄이 없으면 없음(`false`), 도면 자체가 불분명하면 `null`.
- **로드뷰**: 실제 도로를 가로지르는 **단독 흰색 정지선**만 검사한다. **흰색/노란색 횡단보도 표시(연속 반복된 줄무늬)는 정지선이 아니다.** 횡단보도만 보이는 경우 해당 가로줄을 정지선으로 판정하지 않으며, 실제 정지선이 있는지 불분명하면 `null`.
- **로드뷰 정지선 threshold**: 검출 신뢰도 하한값 `analysis.stop_line_roadview_threshold` (기본값 `0.68`, 허용 `0.35~0.95`). UI에서 조정 가능하며 로컬 `config.yaml`에 보관한다. **검수 ID는 저장하지 않는다.**
- **PASS**: 입력툴/로드뷰 유무가 모두 판별되고 동일함(`true/true` 또는 `false/false`).
- **FAIL**: 입력툴/로드뷰 유무가 모두 판별되고 다름(`true/false` 또는 `false/true`).
- **REVIEW(검수 필요)**: 두 화면 중 어느 한쪽이라도 `null`, 횡단보도/정지선 구분 불가, 사진 가림, threshold 미달. 사용자가 추가 확인한다.
- **초기 인식**: 현재 판정은 영상 기하학·색상 기반 *후보 검출*이므로 특히 `FAIL` 결과는 사람이 오탐 여부를 확인한다. 단순히 밝은 가로줄 하나를 찾았다고 횡단보도를 실제 정지선으로 확정해서는 안 된다.
- 판정값은 `staged_analysis.json` 내 `stages.before.comparison.stop_line.verdict`(`PASS/FAIL/REVIEW`), UI 및 근거 이미지에 기록한다. threshold는 `summary.stop_line_roadview_threshold`에도 남긴다.

## 4. 진입 후 검수 항목 — 좌·직·우 각각

| 항목 코드 | 입력툴 기대값 | 로드뷰 관측값 |
|---|---|---|
| `road_exists` | 해당 진출 방향 도로가 존재하는지 | 촬영 방향 전방의 실제 도로 또는 건물 등 비도로 영역 |
| `exit_lane_count` | 해당 방향 진출 차로 수 | 실제 해당 진행 방향 차로 수 |
| `guidance_line` | 일반 유도선 존재·개수 | 일반 유도선 존재·개수 |
| `colored_guidance` | 컬러유도선 존재·색·개수 | 실제 컬러유도선 존재·색·개수 |

**차로 수 0 및 도로 없음(`false`)**은 충분한 관측 근거가 있을 때만 사용한다. 가림·사진 누락·잘못된 시점·인식 실패는 **`null`(판단 불가)**로 기록한다.

### 도로와 건물 비교 — 초기 판정 기준(현장 보정 예정)

- 사용자가 해당 방향으로 로드뷰를 향하게 한 다음 찍은 **전방 중앙 영역**에서 도로/건물 픽셀을 분할한다.
- 입력툴의 해당 방향 경로가 확인되고 로드뷰 중앙에서 도로가 확인되면 **일치 후보**로 기록한다.
- 입력툴의 해당 방향 도로가 확인되는데 **로드뷰 전방 중앙에 건물 영역이 우세하고 도로 영역이 거의 없으면 불일치 의심**을 기록한다.
- 다른 방향의 건물, 도로변의 건물, 일시적 가림은 **도로가 없다는 근거로 사용하지 않는다**.
- 촬영 위치/각도가 맞지 않거나 두 화면 중 예상값을 읽지 못한 경우 **판단 보류**.

실제 사진으로 오탐/미탐을 확인한 뒤 전방 ROI·모델·임계값을 변경한다. 현재 수치가 보편적인 확정 기준이라는 뜻은 아니다.

## 5. 향후 데이터 비교용 교차로 스코어(확정 저장 규칙)

**검수 ID(Polygon ID - Link ID)별 여섯 개의 도로 영역 스코어를 반드시 기록한다.**

| 촬영 단계 | 기록할 값 | CSV 필드 |
|---|---|---|
| 진입 전 | 왼쪽 ROI 점수 | `before_left_score` |
| 진입 전 | 중앙 ROI 점수 | `before_straight_score` |
| 진입 전 | 오른쪽 ROI 점수 | `before_right_score` |
| 진입 후 · 좌 | 좌회전 시점 사진 **정면 ROI 점수** | `after_left_straight_score` |
| 진입 후 · 직 | 직진 시점 사진 **정면 ROI 점수** | `after_straight_straight_score` |
| 진입 후 · 우 | 우회전 시점 사진 **정면 ROI 점수** | `after_right_straight_score` |

점수 공식: **해당 ROI에서 SegFormer가 road로 분할한 픽셀 수 ÷ 해당 ROI 전체 픽셀 수**. 값은 0~1, 소수점 6자리까지 저장한다. 전체 점수는 같은 모델·계산식·세로 영역(y=28~60%)을 사용한다. 가로는 왼쪽 4~34%, 중앙 35~65%, 오른쪽 66~96%다.

좌/직/우 **진입 전 스코어와 각 방향으로 들어온 후 정면 스코어의 차이(후-전)**도 방향별로 기록한다. 하지만 두 사진은 시점이 달라 스코어 차이를 실제 도로선형 일치/불일치의 **최종 판정 근거로 삼지 않는다**. 통계·추가 모델 학습과 향후 분석 기준 개선을 위한 정량 자료다.

- **미촬영, 모델 오류, 사진 누락:** `null`, 통합 CSV에서는 공란으로 보관. **0과 구분**.
- **실제로 road 픽셀이 0개:** `0.0`으로 보관. 이것만으로 도로가 실제 없다는 판정은 불가.
- **부분 촬영:** 확보된 점수만 저장하고 누락된 필드를 표시한다.
- **근거 추적:** 모델 이름, 점수 방법 버전(`road_mask_roi_v1`), 각 단계 촬영 revision/이미지 경로, 분석 시각 보관.
- **개별 저장:** `<검수 ID>/road_scores.json`, 분석 시각별 `score_history/` JSON.
- **통합 저장:** `output.directory/road_scores.csv`에 검수 ID당 최신 한 행. 재분석해도 다른 검수 ID의 행은 유지한다.
- 선택한 Polygon/Link는 결과 파일에만 저장하며 `config.yaml`에 저장하지 않는다.
- 수치 계산 기준을 현장 테스트 결과로 바꾸면 **점수 버전과 디자인 문서를 함께 변경**해 과거 자료와 구분한다.

## 6. 결과 형식 및 사람 검수

- 촬영 기록: `staged_capture.json` (단계별 revision, 입력툴/로드뷰 원본 경로, 촬영 시각)
- 분석 기록: `staged_analysis.json` (단계별 `input_expected`, `roadview_observed`, `comparison`, `evidence`, `human_review`)
- 표시용 근거 이미지: `overlays/`. 원본 사진과 기존 `result.json` 등은 변경하지 않는다.
- 값과 판정 상태는 분리하며 `null`과 실제 0/`false`를 혼동하지 않는다.
- 비교 상태: `match_candidate`(일치 후보), `mismatch_review`(불일치 의심), `insufficient_evidence`(판단 보류), `not_applicable`(해당 없음), `not_analyzed`(분석 전).
- **일치 후보와 불일치 의심 모두 사람이 최종 확인한다.** 시스템은 자동 승인·업무 입력툴 수정 없음.

## 7. 초기 구현 한계 및 현장 보정

- 기존 SegFormer를 이용한 **도로/건물 마스크 후보**와 입력툴 **색상 선형** 비교는 초기 단계의 사진 인식이다.
- 시안색 가로 정지선과 로드뷰 단독 흰색 정지선의 **존재 여부 비교**는 초기 검출기로 구현했다. **횡단보도는 정지선이 아니다.** 로드뷰 단독선 여부가 애매하면 `REVIEW`로 남기고 사용자가 판정한다.
- 색상 유도선은 여전히 시각적 후보 검출로, 다른 노면표시와 혼동할 수 있다.
- 차로 수, 노면 화살표의 복합 모양, 일반 유도선 개수, 실제 유도선 색·개수 등은 정확한 모델과 입력툴 표기 방식 검증 전까지 임의 추정치를 기록하지 않고 판단 보류한다.
- 실제 지도 좌표와 로드뷰 카메라 포즈가 없는 한 **정밀 3D 도로 정합**을 확정할 수 없다.

### 현장 테스트 요구사항 접수 규칙

1. 사용자가 진입 전/좌/직/우를 하나씩 테스트하며 새로운 요구사항·오류 사례를 전달할 수 있다.
2. 기존 요구사항·컨셉과 비교해 **확정할 내용/검토 중인 내용**을 나눈다.
3. 확정된 검수 기준은 **이 문서에 추가**하고 영향을 받은 [프로젝트 컨셉](PROJECT_CONCEPT.md), [디자인](INTERSECTION_REVIEW_DESIGN.md), 코드도 함께 수정한다.
4. 컨셉과 충돌하면 사용자에게 먼저 묻는다. 사용자가 명시적으로 컨셉 갱신을 지시했다면 즉시 반영한다.
5. **요청받지 않은 테스트 코드 작성이나 테스트 실행은 하지 않는다.**

## 8. 현재 구현·후속 검증

- **구현**: 수동 4단계 촬영, 두 창의 WGC 캡처, 사진 쌍 이력, 단계 상태, 저장 사진 분할·비교, 건물/도로 후보, UI 근거 요약.
- **구현**: 같은 도로 모델을 활용해 진입 전 좌/직/우 + 진입 후 좌/직/우 정면 총 6개 스코어와 차이, 개별 JSON 이력 및 전체 CSV 저장.
- **초기 후보 수준**: 입력툴 시안색 가로 정지선 및 로드뷰 단독 흰색 정지선/횡단보도 구별, threshold 기반 `PASS/FAIL/REVIEW`, 컬러 선 후보, 입력툴 색상 선형에 따른 기대 방향.
- **추가 보완/현장 검증**: 차로 수·화살표·일반/컬러유도선 개수, 카메라/지도 정합, 건물 오탐, 차로 경계, 건물 뒤의 도로.
- **실환경 미검증**: Windows 업무 프로그램에서 정확도·촬영 상태·AI 실행 결과는 사용자의 단계별 확인을 거쳐 보정한다.

### 현장 요청: 입력툴 방향 후보와 결과 표시

- 결과 화면에 입력툴의 좌·직·우 도로 존재 후보와 후보 점수를 표시한다. 현재 색상 경로 연결 후보의 점수 0.62는 고정 휴리스틱이며 확률이 아니다. 경로가 불명확하거나 촬영되지 않으면 판단 보류한다.
- 각 방향의 색상 선형 회전각 후보를 표시한다. P/F/PA 등 선형 코드 문자 판독은 아직 구현되지 않아 판독 불가로 표시한다.
- 진입 후 도로 존재는 각 방향으로 촬영한 사진의 전방 중앙을 독립적으로 확인한다. 진입 전후 점수 차이는 화면에 표시하지 않는다. 기존 CSV/JSON의 차이 필드는 저장 호환성을 위해 유지하며 판정 근거로 사용하지 않는다.
