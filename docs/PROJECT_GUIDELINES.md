# map_validator 프로젝트 개발·문서 운영 지침

> 효력: 이 프로젝트에서 코드, UI, 데이터 구조, 설정 또는 문서를 수정할 때 적용
> 시작 파일: [AGENTS.md](../AGENTS.md)
> 기준: [프로젝트 컨셉](PROJECT_CONCEPT.md) → [요구사항](REQUIREMENTS.md) → [4단계 검수 디자인](INTERSECTION_REVIEW_DESIGN.md) → [기존 UI](UI.md)

## 1. 작업 전 지침서 필수 확인

**프로젝트 코드 작업을 시작하기 전에 지침서를 반드시 확인한다.**

순서:
1. `AGENTS.md` 및 현재 문서 `docs/PROJECT_GUIDELINES.md`
2. `docs/PROJECT_CONCEPT.md`: 프로젝트 목적, 촬영 방식, 사용자 통제 범위, 금지 동작
3. `docs/REQUIREMENTS.md`: 비교할 항목, 판정 상태, 현장 테스트에서 확정한 요구사항
4. `docs/INTERSECTION_REVIEW_DESIGN.md`: UI, 단계별 촬영, 파일명/결과 구조
5. 수정 파일과 직접 관련된 문서: `docs/UI.md`, `docs/LINE_GEOMETRY.md`, `docs/ARCHITECTURE.md` 등

지침을 읽지 않고 관성적으로 예전 기능을 복구하거나 새 자동화를 추가하지 않는다. 이전 대화나 옛 코드가 최신 문서와 충돌할 경우 최신 합의된 컨셉을 확인한다.

## 2. 컨셉 우선·충돌 시 사용자 확인

- 변경사항은 프로젝트 컨셉에 맞게 설계하고 구현한다.
- **요청과 기존 컨셉이 충돌하면 먼저 사용자에게 확인**한다. 사용자가 정해주기 전에는 임의로 컨셉을 뒤집거나 코드를 변경하지 않는다.
- 예시: “사용자가 직접 4번 촬영”이라는 컨셉과 “프로그램이 로드뷰를 자동으로 움직여 촬영”하는 제안은 충돌하므로 확인이 필요하다.
- 사용자 승인으로 컨셉이 변경되면 `PROJECT_CONCEPT.md`, `REQUIREMENTS.md`, 디자인 문서를 맞춰 갱신한 뒤 코드를 구현한다.
- 현장에 영향을 주는 변경인데 요청의 의미가 불명확하면 한 번의 구체적인 질문으로 확인한다. 반면 이미 명시적으로 합의된 사항을 반복해서 묻지 않는다.

## 3. 컨셉 업데이트 여부 확인

**새 기능이나 기준 변경이 제안되면, 그것이 컨셉 변경인지 판별하고 컨셉도 업데이트할지 묻는다.**

- 촬영 단계, 사용자 조작 범위, 검수 대상, 판정/결과의 의미, 데이터 보관 정책 변화: 컨셉 영향이 있으므로 업데이트 여부 확인
- 기존 컨셉 안에서의 디자인 수정, 코드 정리, 버그 수정: 컨셉 변경이 필요 없으면 기존 문서 기준으로 작업
- 사용자가 이미 “컨셉 업데이트해”라고 명시한 경우: 다시 묻지 말고 해당 문서를 수정
- 사용자 승인 없는 컨셉 변경을 코드 구현의 전제로 만들지 않는다

## 4. 코드 변경 시 디자인 문서 동기화

**코드가 변경되면 관련 디자인 문서도 반드시 함께 업데이트한다.**

영향별 최소 동기화 대상:

| 변경 종류 | 함께 갱신할 문서 |
|---|---|
| UI 버튼/레이아웃/상태/촬영 순서 | `INTERSECTION_REVIEW_DESIGN.md`, `UI.md` |
| 촬영 종류·파일명·폴더·재촬영·JSON 구조 | `INTERSECTION_REVIEW_DESIGN.md`, `FOLDER_STRUCTURE.md` |
| 정지선·차로·화살표·유도선 인식 규칙 | `REQUIREMENTS.md`, `INTERSECTION_REVIEW_DESIGN.md` |
| 지도 선형·3D 로드뷰 비교 기준/판정 의미 | `LINE_GEOMETRY.md`, `REQUIREMENTS.md` |
| 사용자 흐름·자동화 범위·안전 제약 | `PROJECT_CONCEPT.md`, `INTERSECTION_REVIEW_DESIGN.md` |
| 설치·필요 라이브러리·실행법 | `README.md`, `UI.md` |

구현하지 않은 목표를 “현재 동작”으로 쓰지 않는다. 구현 상태는 **현재 구현/설계/미구현/검증 필요**를 명시한다. 문서와 코드의 동작이 서로 모순되지 않도록 같은 작업에서 갱신한다.

## 5. 현장 테스트와 요구사항의 지속적 변경

**사용자가 기능을 하나씩 직접 테스트하면서 새로운 검수 항목이나 예외 사례를 발견할 수 있고, 그때마다 요구사항이 추가·수정될 수 있다.** 이것은 정상적인 개발 과정이다.

새 요구사항을 받으면 다음 정보를 정리한다:
- 어떤 촬영 단계(진입 전/좌/직/우)에서 발생했는지
- 입력툴 기대값과 실제 로드뷰 관측값이 무엇인지
- 기존 규칙으로 왜 처리되지 않는지
- 바꿔야 할 비교 기준·UI·데이터 구조가 무엇인지
- 해당 기준이 **확정**인지, 실험적으로 **검토 중**인지

사용자가 확정한 사항은 `docs/REQUIREMENTS.md`의 관련 항목에 추가한다. 아직 판단되지 않은 사항은 “검토 중”으로 분리한다. **기존 요구사항과 충돌하면 사용자에게 먼저 묻는다.**

추가 요구로 컨셉·디자인에 영향이 생기면 같은 변경에서 문서를 수정한다. 현장 테스트 한 번의 임시 결과만으로 일반화하거나 미확인 추정치를 확정 기준으로 승격하지 않는다.

## 6. 코드 구현 시 적용할 기술·안전 원칙

### 캡처·입력툴 보호

- 사용자가 직접 로드뷰 시점·위치를 조절한다. **진입 전·좌·직·우 네 방향은 도로가 없어도 모두 촬영한다.** 소프트웨어의 자동 이동/회전/Zoom은 4단계 UI 흐름에 넣지 않는다. 촬영을 건너뛰는 '도로 없음' 버튼을 만들지 않는다.
- 촬영은 기존 **WGC**로 `HD_3D Tool`과 `NLadybugSv` 두 창을 캡처한다.
- `HD_3D Tool`의 실제 그래픽 화면이 하얗게 변했던 이력이 있다. **`PrintWindow` 재사용·폴백 금지**, 임의 창 활성화/복원/이동/크기 변경/Zoom 변경 금지.
- 캡처 실패 시 다른 캡처 방법으로 몰래 재시도하지 말고 오류 원인과 사용자 조치를 안내한다.

### 검수 정확성

- **입력툴 기대값과 로드뷰 관측값**은 서로 별도 필드로 관리한다.
- 실제 도로 없음 후보/차로 0과 사진 누락/인식 불가를 구별한다(`false`/`0`과 `null` 차이). **입력툴이 도로를 예상하지만 로드뷰 전방에 건물 등 비도로가 우세하고 도로가 거의 없으면 불일치 의심**으로 표시하되, 사진에 건물이 등장했다는 사실만으로 확정하지 않는다.
- 시안색 진입 선형과 시안색 가로 정지선은 동일하게 취급하지 않는다.
- 좌/직/우의 각기 다른 촬영 단계·방향을 섞어 비교하지 않는다.
- 출력은 “일치 후보/불일치 의심/판단 보류” 등 **검수 보조 정보**다. 최종 승인·자동 업무 입력은 하지 않는다.
- 분석·재분석은 기존 원본 PNG를 바꾸지 않으며, 표시용 오버레이·결과 JSON을 분리한다.

### 데이터·성능·구조

- 사용자의 선택 Polygon/Link ID는 UI에서 갱신하고 `config.yaml`에 저장하지 않는다.
- 원본 스크린샷, 개인정보, 업무 데이터, 서버 키, 로컬 `config.yaml`, 촬영 이력은 공개 GitHub에 올리지 않는다.
- Windows UI Automation·AI 분석은 GUI 이벤트 루프를 막지 않는 작업 스레드에서 수행한다.
- 이미지 처리 로직은 `map_validator/`, UI 구성은 `UI/`로 분리하고, 모듈을 불필요하게 복제하지 않는다.
- 불필요한 주기 조회, 창 상태 변경, 반복 AI 모델 로딩 등을 피하고 성능이나 메모리 사용을 고려한다.
- 데이터 마이그레이션은 이전 검수 기록을 보존하며 이전 파일에 대한 호환을 고려한다.

## 7. 질문·테스트·작업 요청 구분

- “가능한가?”, “왜 그런가?”, “어떻게 생각해?” 등 **질문만 받은 경우 실제 파일 수정이나 커밋을 하지 않고 분석·설명만 한다.**
- “구현해줘”, “문서에 적어줘”, “메인에 커밋해줘” 등 **실행 지시가 있을 때만** 수정한다.
- **테스트 코드 작성과 자동 테스트 실행은 사용자가 명시적으로 요청한 경우에만** 수행한다.
- 코드 정적 검토 및 커밋 후 해당 파일을 다시 읽어 변경 사실을 확인하는 것은 허용한다.
- 실행하지 않은 테스트를 성공했다고 말하지 않는다. 현장 프로그램을 직접 조작·확인할 수 없을 때는 그 한계를 명시한다.

## 8. GitHub 변경 관리와 결과 보고

1. 사용자 지시가 있는 브랜치로만 작업한다. 현재 사용자가 직접 `main` 커밋을 요청한 범위에서는 `main`에 문서를 반영한다.
2. 서로 다른 파일을 수정할 때 의도와 범위를 구체적으로 관리한다.
3. 새 컨셉·요구사항이 추가되면 관련 문서 링크와 변경 이력을 업데이트한다.
4. 코드/문서 커밋 후 실제 커밋 SHA 또는 링크를 확인해 전달한다.
5. 구현과 문서화, 실환경 검증 여부를 명확히 구분한다.

## 10. 문서 우선순위와 갱신 책임

지침서와 컨셉이 충돌하거나 두 요구사항이 서로 모순되는 경우 **임의로 더 편한 쪽을 선택하지 않는다**. 사용자에게 충돌과 선택지를 설명하고 확정한 뒤 정정한다.

사용자가 **현장 테스트에서 단계별로 발견하는 추가 요구사항은 지속적으로 `REQUIREMENTS.md`에 업데이트 가능**하다. 프로젝트 컨셉을 유지하며 검수 규칙을 정교화하는 것이 기본이고, 컨셉 자체를 바꾸는 추가 요구는 사용자와 먼저 합의한다.
