## 1. 사용자 중심 설계

검수자가 **직접 촬영 위치와 로드뷰 시점을 조정**한다. 프로그램은 사용자가 촬영 버튼을 누르는 순간 열린 **HD_3D Tool + NLadybugSv**의 화면을 **WGC로 각각 촬영**하여 해당 검수 ID와 단계에 보관한다. 분석은 저장 사진만 사용하며 촬영과 분리한다.

**고정된 4개 타입과 안내 순서**

| 번호 | 코드 | 화면 버튼 | 촬영 내용 |
|---|---|---|---|
| 1 | `before` | 진입 전 촬영 | 정지선·진입 차로·노면 화살표·컬러유도선 |
| 2 | `after_left` | 진입 후 · 좌 | 좌측 진출 도로·차로·유도선 |
| 3 | `after_straight` | 진입 후 · 직 | 직진 진출 도로·차로·유도선 |
| 4 | `after_right` | 진입 후 · 우 | 우측 진출 도로·차로·유도선 |

기본 촬영 순서는 **진입 전 → 좌 → 직 → 우**이며 사용자가 단계별로 다시 촬영할 수 있다. **도로가 실제로 없는 방향도 반드시 촬영한다.** 건물·비도로 영역이 실제 보이는지를 프로그램이 분석해야 하므로 도로 없음 버튼으로 촬영을 건너뛰지 않는다.

## 2. 화면 구조

기존 PyQt6 작은 반투명 창·드래그 헤더·로그·창 제목 설정을 유지하되, 촬영 단계를 카드처럼 명확히 보여주고 작은 창에서는 세로 스크롤한다.

~~~text
┌────────────────────────────────────────────────┐
│ map_validator                          [―] [X]│
│ 검수 ID     [Polygon ... - Link ...          ] │
│ 입력툴      [HD_3D Tool              ][선택] │
│ 로드뷰      [NLadybugSv              ][선택] │
│ 저장 경로   [C:\...\result           ][찾기] │
├────────────────────────────────────────────────┤
│ 1 / 4  [진입 전 촬영]       ● 촬영 완료 [재촬영]│
│ 2 / 4  [진입 후 · 좌]       ○ 미촬영 [촬영]     │
│ 3 / 4  [진입 후 · 직]       ○ 미촬영 [촬영]     │

│ 진입 후 좌  도로 [?] 차로 [?] 일반 [?] 컬러 [?]│
│ 진입 후 직  미촬영                             │
│ 진입 후 우  도로 [!] 차로 [!] 일반 [?] 컬러 [?]│
~~~

*컨셉 화면으로, 현재 구현된 UI 화면이 아니다.* 상태 표시는 색이나 기호에만 의존하지 않고 텍스트를 병기한다.

### 촬영 상태

| 상태 코드 | 표기 | 의미 |
|---|---|---|
| `not_captured` | 미촬영 | 아직 사진 쌍 없음 |
| `captured` | 촬영 완료 | 입력툴·로드뷰 각각 1장 정상 저장 |
| `partial_capture` | 부분 실패 | 둘 중 한 장이 누락/저장 실패 |
| `needs_recapture` | 재촬영 필요 | 화면 가림·화질 문제·사용자 재촬영 요청 |
| `analysis_complete` | 분석 완료 | 해당 단계의 분석 결과가 저장됨 |

좌·직·우는 **도로가 없어도 모두 촬영**하며, 도로가 없다는 판단은 사진의 도로·건물 마스크와 입력툴 경로를 대조한 **분석 결과**다. **미촬영 ≠ 도로 없음 후보**이다. 재촬영 시 기존 자료를 덮어쓰지 않고 버전 이력을 보존한다. 분석 후 재촬영하면 이전 분석은 구버전 사진 기반으로 처리하고 최신 사진으로 다시 분석한다.

## 3. 검수 항목과 비교 화면

### 교차로 진입 전

| 코드 | 입력툴의 기대 정보 | 로드뷰의 실제 관측 | 비교 방법 |
|---|---|---|---|
| `stop_line` | **시안색 가로 정지선** 유무 | **횡단보도와 분리된 단독 흰색 정지선** 유무 | 입·출력의 `true/false`가 같으면 `PASS`, 다르면 `FAIL`, 불분명하면 `REVIEW` |
| `entry_lane_count` | 진입 방향 차로 수 | 실제 진입 차로 수 | 정수 값 비교, 차선 가림 시 보류 |
| `lane_arrows` | 차로별 좌·직·우 및 복합 화살표 | 실제 노면 화살표 | 차로별 위치와 조합까지 비교 |
| `colored_guidance` | 컬러유도선 유무·색상·개수 | 실제 컬러유도선 유무·색상·개수 | 조명·마모·가림 때문에 불명확하면 보류 |

### 정지선 유무 비교 디자인 · 실험적 구현

진입 전(`before`) 촬영본에서만 **정지선 존재 여부**를 대조한다.

- **입력툴:** 검은 도면에서 **시안색 가로줄**이 정지선 기준이다. 시안색 세로 진입 경로 또는 다른 색의 도로선은 정지선이 아니다.
- **로드뷰:** 실제 도로의 **흰색 단독 정지선**만 후보로 인정한다. 횡단보도(흰색/노란색 반복 줄무늬)와 구분하고, 횡단보도만 있는 장면에서 자동으로 정지선 존재라고 하지 않는다.
- **threshold 조절:** UI의 **로드뷰 정지선 threshold** (`0.35~0.95`, 초기 `0.68`). 높을수록 로드뷰의 정지선 유무를 더 엄격히 판정하고, 부족하면 수동 검수를 요청한다. 설정 키 `analysis.stop_line_roadview_threshold`; 개인 설정 `config.yaml`에 저장.
- **정지선 전용 결과:** `PASS`(존재 여부 같음), `FAIL`(다름), `REVIEW`(둘 중 하나 이상 불명확). 일반적인 도로 후보 상태(`match_candidate/mismatch_review/insufficient_evidence`)는 호환을 위해 함께 기록.
- **근거:** 도면에서 검출한 시안색 가로선과 로드뷰에서 발견한 단독 흰색 정지선을 `overlays/before_*_input.png` 및 `overlays/before_*_roadview.png`에 표시. 불명확한 사진에서는 선을 만들어 그리지 않는다.
- **기록:** `staged_analysis.json`의 `stages.before.comparison.stop_line.verdict`, `stages.before.stop_line_verdict`, `summary.stop_line_verdict`, `summary.stop_line_roadview_threshold`.
- **현장 보정:** 검출 점수와 횡단보도·정지선의 실제 위치를 여러 사진으로 검토한 뒤 임계값/영역을 개선한다. **FAIL이라도 사람의 최종 검수가 필요**하다.

### 교차로 진입 후 (좌 / 직 / 우 각각)

| 코드 | 입력툴의 기대 정보 | 로드뷰의 실제 관측 |
|---|---|---|
| `road_exists` | 해당 진출 방향 도로 존재 여부 | 그 방향의 실제 도로 존재 여부 |
| `exit_lane_count` | **해당 진행 방향** 진출 차로 수 | 실제 동일 방향 차로 수 |
| `guidance_line` | 일반 유도선 존재·개수 | 실제 일반 유도선 존재·개수 |
| `colored_guidance` | 컬러유도선 존재·색상·개수 | 실제 컬러유도선 존재·색상·개수 |

차로 **0** 또는 도로 없음은 명확한 근거가 있을 때만 기록한다. 인식 실패·사진 누락은 `null`/판단 보류다. **입력툴에 도로가 예상되는데 로드뷰 전방에 건물이 우세하고 도로가 거의 없으면 `mismatch_review` 후보**로 표시한다. 화면 한쪽 건물이나 건물 뒤의 도로까지 부재로 간주하지 않는다. 실제 전방 중심 영역(ROI)과 임계값은 단계별 현장 테스트 결과로 보정한다. 일반 차선 경계선과 유도선은 분리해야 한다.

### 항목별 결과 표

각 항목은 **입력툴 기대값 / 로드뷰 관측값 / 비교 상태 / 판단 사유 / 근거 이미지**를 표시한다.

| 비교 상태 | 표기 | 정의 |
|---|---|---|
| `match_candidate` | 일치 후보 | 동일 항목의 값이 맞는 정황 |
| `mismatch_review` | 불일치 의심 | 값이 다르거나 선형 연결이 맞지 않을 가능성 |
| `insufficient_evidence` | 판단 보류 | 이미지 부족·가림·인식 불확실·기준 모호 |
| `not_applicable` | 해당 없음 | 확인된 도로 부재 등 해당 항목 비교 불필요 |
| `not_analyzed` | 분석 전 | 아직 실행 안 됨 |

어떤 항목도 AI 결과만으로 최종 승인하지 않는다. **정지선·차로 수·노면 화살표·유도선 인식은 향후 구현 및 현장 검증 대상**이며, 기존 색상 선형 비교 코드가 곧바로 이 항목들을 정확히 판독한다는 의미가 아니다.

## 4. 진입 전·진입 후 스코어 비교 패널

분석 결과 창 상단에 아래처럼 **동일 검수 ID의 여섯 개 수치**를 별도 표시한다. 데이터는 로드뷰 마스크에서 계산하며 기존 항목별 입력툴↔로드뷰 정합 판정과 구분한다.

```text
검수 ID: Polygon 480706989- Link 361
                    좌측      직진      우측
교차로 진입 전    0.1234    0.5678    0.2345
교차로 진입 후    0.3400    0.7200    0.1300
입력툴            좌 후보/보류 | 직 후보/보류 | 우 후보/보류
도로 선형         좌 P | 직 F | 우 N  (일치 후보 / 불일치 의심 / 판단 보류 예시)
```

*수치는 레이아웃 예시일 뿐 실제 분석값이 아니다.*

**진입 후의 세 값은 각각 다른 촬영 사진의 중앙(정면) 도로 스코어다.** 좌·직·우 사진을 한 장으로 합치거나, 진입 후의 좌측 픽셀 비율을 '좌회전 스코어'로 사용하지 않는다.

- 스코어 범위: `0.0–1.0`. **도로 AI 마스크에서 지정 ROI의 도로 픽셀 수 ÷ 전체 ROI 픽셀 수**.
- 진입 전: 사진 한 장에서 `left: x=4–34%`, `straight: x=35–65%`, `right: x=66–96%`를 사용한다.
- 진입 후 좌·직·우: 각 사진에서 **동일한 중앙 x=35–65%** ROI의 점수를 사용한다.
- 세로 ROI: **y=28–60%** (모든 값 동일), 이미지 크기가 달라도 비율 좌표로 계산한다.
- 같은 모델/점수 계산 버전을 기록한다. 전후 스코어 차이는 화면에 표시하지 않는다. 기존 JSON/CSV 저장 형식의 차이 열은 호환성 때문에 유지하며 판정에 사용하지 않는다.
- 입력툴 방향별 존재 후보는 해당 진입 후 사진의 색상 경로가 해당 방향으로 연결된 경우에만 `있음`, 고정 휴리스틱 점수 0.62로 표시한다. 그 밖에는 판단 보류다. 이 점수는 확률이 아니다. 도로 선형 행은 각 방향 입력툴 및 로드뷰 전방 도로 존재 비교의 상태를 P(일치 후보), F(불일치 의심), N(판단 보류)으로 표시한다. 실제 도로 형상 일치를 검증한 판정은 아니다.
- 진입 후 도로 존재는 각 사진의 전방 중앙 ROI에서 도로·건물 비율로 판단하며, 위 6개 스코어의 중앙 ROI와 판정 ROI는 서로 다르다.
- 미촬영·분석 실패: 점수 `null`/CSV 공란. 실제 도로 픽셀 0개인 경우만 `0.0`.
- 4단계 중 일부만 있어도 **있는 스코어부터 저장**한다. 점수가 비었다고 도로가 없는 것으로 판단하지 않는다.
- 본문 항목별 비교표(차로·정지선·유도선)는 기존대로 유지한다.

### 보관 형식

- **검수 ID 개별 최신 기록:** `<결과 폴더>/road_scores.json`
- **검수 ID별 분석 이력:** `<결과 폴더>/score_history/road_scores_<timestamp>_<id>.json`
- **전체 교차로 요약:** `<output.directory>/road_scores.csv` — 검수 ID당 최신 한 행, UTF-8 BOM으로 Excel에서도 열기 쉽도록 저장.
- **기존 분석 결과:** `staged_analysis.json`에도 동일 스코어 객체 포함.

통합 CSV의 기준 열:

| 검수 ID | 진입 전 좌 | 진입 전 직 | 진입 전 우 | 진입 후 좌(정면) | 진입 후 직(정면) | 진입 후 우(정면) |
|---|---|---|---|---|---|---|
| `case_id` | `before_left_score` | `before_straight_score` | `before_right_score` | `after_left_straight_score` | `after_straight_straight_score` | `after_right_straight_score` |

추가 열: `polygon_id`, `link_id`, 좌·직·우 차이, 촬영 버전 4개, 스코어 방식과 모델, 분석 시각, 누락 스코어 목록.

**재분석 시 전체 CSV는 해당 검수 ID 최신 행만 갱신**하지만, 과거 측정값은 이력 JSON으로 남긴다. 같은 교차로의 다른 시점·모델·ROI 점수는 점수 방법 버전과 근거 이미지가 일치하는지 확인 후 비교한다.

## 5. 사용 흐름과 오류 대응

1. 교차로 Polygon/Link 선택 → 기존 **클릭 기반 검수 ID 갱신**.
2. 사용자가 로드뷰와 입력툴 화면을 직접 맞추고 단계별 촬영 버튼 클릭.
3. 클릭 시 두 창을 **WGC로만 촬영**. 이동·활성화·크기 변경·Zoom 설정·최소화 복원·자동 W/S 입력 없음.
4. 도로 없는 방향도 촬영해 두 장을 단계별 쌍으로 관리하고 현재 ID의 단계별 상태 갱신.
5. **촬영본 분석**: 저장된 단계별 사진에서 입력툴 예상 경로와 로드뷰 도로/건물 후보를 비교. **재촬영 없음.**
7. 근거 사진, 차이, 보류 사유를 확인하고 사용자가 최종 검수.

**오류/경계조건:** 대상 창 최소화→자동 복원 금지; 일부만 캡처 성공→`partial_capture`; 특정 단계 누락→나머지 단계의 부분 분석 허용하고 전체 완료 아님; 다른 검수 ID로 이동→해당 ID의 상태를 다시 읽음; AI 모델 지연·오류→기존 사진·이력 보존; 결과 충돌→무조건 일치로 합치지 않음.

## 6. 저장 데이터·호환성

권장 새 구조 (**기존 평면 PNG/`result.json` 유지**):

~~~text
output.directory/
├── road_scores.csv  # 모든 검수 ID의 최신 스코어 한 행씩
└── Polygon ...- Link .../
    ├── captures/
    │   ├── before/          # *_before_HD_3D Tool.png / *_before_NLadybugSv.png
    │   ├── after_left/      # *_after_left_...
    │   ├── after_straight/  # *_after_straight_...
    │   └── after_right/     # *_after_right_...
    ├── staged_capture.json  # 단계 상태·원본 참조·재촬영 버전
    ├── staged_analysis.json # 각 항목 기대/관측/상태/근거·사유
    ├── road_scores.json     # 6개 방향별 최신 도로 스코어
    ├── score_history/       # 분석 회차별 스코어 JSON 이력
    ├── overlays/            # 시안색 정지선, 차선, 유도선 등 표시
    ├── result.json          # 기존 파일 유지
    └── ...기존 PNG           # 기존 파일 보존
~~~

`staged_capture.json`에는 `schema_version`, `case_id`, `stage`, `state`, `revision`, `captured_at`, `work_image`, `roadview_image`, `history` 등의 필드를 사용한다. **`absence_confirmed_by_user`는 새 설계에서 사용하지 않는다.** 새로 캡처된 사진만 단계별 이름으로 저장하며, 기존 원본을 묵시적으로 새 단계에 매핑하지 않는다.

`staged_analysis.json`은 단계별 `input_expected`, `roadview_observed`, `comparison`, `evidence`, `uncertainty`, `human_review`를 포함한다. 차로 수 및 유도선 개수는 인식 실패 `null`과 실제 0개를 구별한다. 수동 수정값은 AI 추정 원본과 별도 보관한다.

## 7. 구현 예정 모듈

| 영역 | 책임 | 상태 |
|---|---|---|
| `UI/app.py` | 4개 촬영 버튼·단계 상태·검수 결과 UI | 초기 구현 완료 · Windows 확인 필요 |
| `UI/worker.py` | 단계별 WGC 촬영·저장 사진 비교 작업 | 초기 구현 완료 · Windows 확인 필요 |
| `map_validator/wgc_capture.py` | 대상 창을 건드리지 않는 WGC 캡처 | 기존 구현 |
| `map_validator/stage_types.py` | 단계/상태/검증 규칙 | 구현 |
| `map_validator/staged_capture.py` | 단계별 쌍 저장·재촬영 이력 | 구현 |
| `map_validator/input_features.py` | 입력툴 기대값 추출 | 정지선·경로 후보 구현 / 개수·화살표 보류 |
| `map_validator/roadview_features.py` | 로드뷰 관측값 추출 | 도로/건물·정지선·컬러 후보 구현 / 개수 보류 |
| `map_validator/staged_compare.py` | 항목별 비교·결과 JSON | 구현 |
| `map_validator/line_geometry.py` | 기존 색상 선형 후보 추정 | 기존 코드 참고 |

**진행 상태:** M1 단계별 촬영/재촬영/상태 초기 구현 → M2 진입 전 항목의 초기 색상·정지선 후보 구현(차로 수·화살표 등 보류) → M3 방향별 도로/건물 후보 구현(차로 수·유도선 개수 등 보류) → M4 결과·근거 UI 초기 구현 → M5 사용자의 한 단계씩 현장 테스트에 따라 임계값·정확도를 보정.

## 8. 변경 관리

- 사용자가 **현장 테스트를 하나씩 진행하면서 새로운 요구사항을 발견할 수 있으며, 요구사항은 지속 업데이트**한다.
- 새 요구사항이 기존 컨셉과 충돌하면 **코드부터 수정하지 않고 사용자에게 확인**한다.
- 새로운 동작 요구 시 **컨셉 업데이트가 필요한지 질문**한다. 사용자가 이미 컨셉 업데이트를 명시했다면 바로 진행한다.
- 코드 변경 시 **관련 디자인 문서도 반드시 동기화**한다.
- 검수 화면·실데이터·로컬 `config.yaml`과 선택된 Polygon/Link ID는 Git에 넣지 않는다.
- 테스트 코드 작성·테스트 실행은 사용자가 요청했을 때만 한다.
