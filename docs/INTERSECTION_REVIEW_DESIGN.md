## 1. 사용자 중심 설계

검수자가 **직접 촬영 위치와 로드뷰 시점을 조정**한다. 프로그램은 사용자가 촬영 버튼을 누르는 순간 열린 **HD_3D Tool + NLadybugSv**의 화면을 **WGC로 각각 촬영**하여 해당 검수 ID와 단계에 보관한다. 분석은 저장 사진만 사용하며 촬영과 분리한다.

**고정된 4개 타입과 안내 순서**

| 번호 | 코드 | 화면 버튼 | 촬영 내용 |
|---|---|---|---|
| 1 | `before` | 진입 전 촬영 | 정지선·진입 차로·노면 화살표·컬러유도선 |
| 2 | `after_left` | 진입 후 · 좌 | 좌측 진출 도로·차로·유도선 |
| 3 | `after_straight` | 진입 후 · 직 | 직진 진출 도로·차로·유도선 |
| 4 | `after_right` | 진입 후 · 우 | 우측 진출 도로·차로·유도선 |

기본 촬영 순서는 **진입 전 → 좌 → 직 → 우**이나 사용자가 단계별로 다시 촬영할 수 있다. 해당 방향의 도로가 **실제로 없을 수 있으므로**, 이를 사진 누락과 구별해 명시적으로 기록한다.

## 2. 화면 구조

기존 PyQt6 작은 반투명 창·드래그 헤더·로그·창 제목 설정을 유지하되, 촬영 단계를 카드처럼 명확히 보여주고 작은 창에서는 세로 스크롤한다.

~~~text
┌────────────────────────────────────────────────┐
│ map_validator                          [―] [X]│
│ 검수 ID     [Polygon ... - Link ...          ] │
│ 입력툴      [HD_3D Tool              ][선택] │
│ 로드뷰      [NLadybugSv              ][선택] │
│ 저장 경로   [C:\...\result           ][찾기] │
├────────────────────────────────────────────────┤
│ 1 / 4  [진입 전 촬영]       ● 촬영 완료 [재촬영]│
│ 2 / 4  [진입 후 · 좌]       ○ 미촬영 [도로 없음]│
│ 3 / 4  [진입 후 · 직]       ○ 미촬영 [도로 없음]│
│ 4 / 4  [진입 후 · 우]       ● 촬영 완료 [재촬영]│
│                 [촬영본 분석] [분석 중지]       │
├────────────────────────────────────────────────┤
│ 진입 전  정지선 [?] 차로 [!] 화살표 [?] 컬러 [?]│
│ 진입 후 좌  도로 [?] 차로 [?] 일반 [?] 컬러 [?]│
│ 진입 후 직  미촬영                             │
│ 진입 후 우  도로 [!] 차로 [!] 일반 [?] 컬러 [?]│
│                                                │
│ [근거 사진 보기] [결과 폴더] [로그 복사]        │
│ 작업 로그 ...                                  │
└────────────────────────────────────────────────┘
~~~

*컨셉 화면으로, 현재 구현된 UI 화면이 아니다.* 상태 표시는 색이나 기호에만 의존하지 않고 텍스트를 병기한다.

### 촬영 상태

| 상태 코드 | 표기 | 의미 |
|---|---|---|
| `not_captured` | 미촬영 | 아직 사진 쌍 없음 |
| `captured` | 촬영 완료 | 입력툴·로드뷰 각각 1장 정상 저장 |
| `partial_capture` | 부분 실패 | 둘 중 한 장이 누락/저장 실패 |
| `road_absent_user_marked` | 도로 없음(사용자 확인) | 좌·직·우 중 해당 진출 도로가 없다고 사용자 표시 |
| `needs_recapture` | 재촬영 필요 | 화면 가림·화질 문제·사용자 재촬영 요청 |
| `analysis_complete` | 분석 완료 | 해당 단계의 분석 결과가 저장됨 |

`도로 없음`은 **좌·직·우 방향별로만** 제공한다. 사용자가 해당 상태를 수정·해제할 수 있어야 하며, **미촬영 ≠ 도로 없음**이다. 재촬영 시 기존 자료를 조용히 덮어쓰지 말고 버전 이력을 보존한다. 분석 후 재촬영하면 이전 분석은 **구버전 사진 기반**으로 표시하고 다시 분석한다.

## 3. 검수 항목과 비교 화면

### 교차로 진입 전

| 코드 | 입력툴의 기대 정보 | 로드뷰의 실제 관측 | 비교 방법 |
|---|---|---|---|
| `stop_line` | **시안색 가로 정지선** 유무 | 실제 정지선 유무 | 시안색 **진입 선형**과 가로 정지선을 혼동하지 않음 |
| `entry_lane_count` | 진입 방향 차로 수 | 실제 진입 차로 수 | 정수 값 비교, 차선 가림 시 보류 |
| `lane_arrows` | 차로별 좌·직·우 및 복합 화살표 | 실제 노면 화살표 | 차로별 위치와 조합까지 비교 |
| `colored_guidance` | 컬러유도선 유무·색상·개수 | 실제 컬러유도선 유무·색상·개수 | 조명·마모·가림 때문에 불명확하면 보류 |

### 교차로 진입 후 (좌 / 직 / 우 각각)

| 코드 | 입력툴의 기대 정보 | 로드뷰의 실제 관측 |
|---|---|---|
| `road_exists` | 해당 진출 방향 도로 존재 여부 | 그 방향의 실제 도로 존재 여부 |
| `exit_lane_count` | **해당 진행 방향** 진출 차로 수 | 실제 동일 방향 차로 수 |
| `guidance_line` | 일반 유도선 존재·개수 | 실제 일반 유도선 존재·개수 |
| `colored_guidance` | 컬러유도선 존재·색상·개수 | 실제 컬러유도선 존재·색상·개수 |

차로가 **0**인 경우는 실제 해당 방향 도로가 없음을 확인한 경우로 제한한다. 인식 실패·사진 누락은 `null` / 판단 보류로 기록한다. 일반 차선 경계선과 유도선을 혼동하지 않으며, 입력툴의 표시 개수·로직이 명확하지 않을 경우 미확인으로 취급한다.

### 항목별 결과 표

각 항목은 **입력툴 기대값 / 로드뷰 관측값 / 비교 상태 / 판단 사유 / 근거 이미지**를 표시한다.

| 비교 상태 | 표기 | 정의 |
|---|---|---|
| `match_candidate` | 일치 후보 | 동일 항목의 값이 맞는 정황 |
| `mismatch_review` | 불일치 의심 | 값이 다르거나 선형 연결이 맞지 않을 가능성 |
| `insufficient_evidence` | 판단 보류 | 이미지 부족·가림·인식 불확실·기준 모호 |
| `not_applicable` | 해당 없음 | 확인된 도로 부재 등 해당 항목 비교 불필요 |
| `not_analyzed` | 분석 전 | 아직 실행 안 됨 |

어떤 항목도 AI 결과만으로 최종 승인하지 않는다. **정지선·차로 수·노면 화살표·유도선 인식은 향후 구현 및 현장 검증 대상**이며, 기존 색상 선형 비교 코드가 곧바로 이 항목들을 정확히 판독한다는 의미가 아니다.

## 4. 사용 흐름과 오류 대응

1. 교차로 Polygon/Link 선택 → 기존 **클릭 기반 검수 ID 갱신**.
2. 사용자가 로드뷰와 입력툴 화면을 직접 맞추고 단계별 촬영 버튼 클릭.
3. 클릭 시 두 창을 **WGC로만 촬영**. 이동·활성화·크기 변경·Zoom 설정·최소화 복원·자동 W/S 입력 없음.
4. 성공한 두 장을 같은 단계의 사진 쌍으로 관리하고 현재 ID의 단계별 상태 갱신.
5. 해당 방향의 도로가 없으면 사용자가 **도로 없음**을 직접 표시·수정.
6. **촬영본 분석**: 저장된 단계별 사진/사용자 표시만 읽고 입력툴·로드뷰 기대/관측값 비교. **재촬영 없음.**
7. 근거 사진, 차이, 보류 사유를 확인하고 사용자가 최종 검수.

**오류/경계조건:** 대상 창 최소화→자동 복원 금지; 일부만 캡처 성공→`partial_capture`; 특정 단계 누락→나머지 단계의 부분 분석 허용하고 전체 완료 아님; 다른 검수 ID로 이동→해당 ID의 상태를 다시 읽음; AI 모델 지연·오류→기존 사진·이력 보존; 결과 충돌→무조건 일치로 합치지 않음.

## 5. 저장 데이터·호환성

권장 새 구조 (**기존 평면 PNG/`result.json` 유지**):

~~~text
output.directory/
└── Polygon ...- Link .../
    ├── captures/
    │   ├── before/          # *_before_HD_3D Tool.png / *_before_NLadybugSv.png
    │   ├── after_left/      # *_after_left_...
    │   ├── after_straight/  # *_after_straight_...
    │   └── after_right/     # *_after_right_...
    ├── staged_capture.json  # 단계 상태·원본 참조·재촬영 버전
    ├── staged_analysis.json # 각 항목 기대/관측/상태/근거·사유
    ├── overlays/            # 시안색 정지선, 차선, 유도선 등 표시
    ├── result.json          # 기존 파일 유지
    └── ...기존 PNG           # 기존 파일 보존
~~~

`staged_capture.json`에는 `schema_version`, `case_id`, `stage`, `state`, `revision`, `captured_at`, `work_image`, `roadview_image`, `absence_confirmed_by_user` 등의 필드를 사용한다. 새로 캡처된 사진만 단계별 이름으로 저장하며, 기존 원본을 묵시적으로 새 단계에 매핑하지 않는다.

`staged_analysis.json`은 단계별 `input_expected`, `roadview_observed`, `comparison`, `evidence`, `uncertainty`, `human_review`를 포함한다. 차로 수 및 유도선 개수는 인식 실패 `null`과 실제 0개를 구별한다. 수동 수정값은 AI 추정 원본과 별도 보관한다.

## 7. 변경 관리

- 사용자가 **현장 테스트를 하나씩 진행하면서 새로운 요구사항을 발견할 수 있으며, 요구사항은 지속 업데이트**한다.
- 새 요구사항이 기존 컨셉과 충돌하면 **코드부터 수정하지 않고 사용자에게 확인**한다.
- 새로운 동작 요구 시 **컨셉 업데이트가 필요한지 질문**한다. 사용자가 이미 컨셉 업데이트를 명시했다면 바로 진행한다.
- 코드 변경 시 **관련 디자인 문서도 반드시 동기화**한다.
- 검수 화면·실데이터·로컬 `config.yaml`과 선택된 Polygon/Link ID는 Git에 넣지 않는다.
- 테스트 코드 작성·테스트 실행은 사용자가 요청했을 때만 한다.
