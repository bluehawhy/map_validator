# map_validator Windows 제어 UI

참고 UI: https://github.com/bluehawhy/nv_c_test (PyQt6, 작은 반투명 상단 고정창, 드래그 헤더, 상태·로그 표시).

## 실행 조건 및 설치

Windows 11과 설치된 호환 Python을 사용합니다. 3.11이 꼭 필요하지는 않습니다. Python 런처에서 사용할 수 있는 버전은 `py list`로 확인합니다.

```powershell
git clone https://github.com/bluehawhy/map_validator.git
cd map_validator
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements-ui.txt
# AI 분석 시에만 추가 설치
python -m pip install -r requirements-ai.txt
python -m UI
```

`python -m UI` 실행 시에는 PyQt6·pywinauto를 불러오기 전에 메인 스레드 COM 모드를 STA로 지정합니다. 이는 COM 모드 충돌 시 MTA에서 STA로 재시도하는 경고의 원인을 줄이며, 경고 메시지 자체를 숨기지는 않습니다. pywinauto 버전에 따라 명시된 COM 설정을 안내하는 별도 메시지는 나올 수 있습니다.

기존 설치 환경에서 업데이트할 때도 **`python -m pip install -r requirements-ui.txt`를 다시 실행**해 주세요. 입력도구와 로드뷰 모두 `windows-capture>=2.0.1`을 통한 WGC(Windows Graphics Capture)로 촬영합니다.

또는 `UI\run_ui.bat`을 실행합니다. 실행할 때 `config.yaml`에 없는 항목만 `config.example.yaml`에서 추가하고, 기존에 들어 있는 항목과 값은 그대로 유지한 뒤 UI를 엽니다. `config.yaml`이 없으면 예제 설정으로 새로 만듭니다.

## 앱 로그

앱 시작, 창 검색, Polygon/Link 선택, 화면 준비, 캡처, 분석, 오류 및 Python 경고를 다음 구조로 표시·저장합니다.

`로그타입 | 날짜 시간 | 코드파일:줄번호 | 로그 텍스트`

예시 (파일명·줄번호는 실제 발생 위치에 따라 달라집니다):

```text
INFO | 2026-11-04 10:55:40.123 | UI/app.py:563 | 시작: analyze / Polygon 480706169- Link 98
WARNING | 2026-11-04 10:55:40.456 | pywinauto/__init__.py:71 | UserWarning: Apply externally defined coinit_flags: 2
ERROR | 2026-11-04 10:55:40.789 | map_validator/windows.py:142 | 작업 오류: zoom label was not exposed through Windows UI Automation | traceback: ...
```

- UI의 **작업 로그** 영역과 콘솔에서 동일 형식을 확인할 수 있습니다. **로그 복사**는 표시된 로그를 복사하며, **로그 폴더**는 저장된 로그 파일 위치를 엽니다.
- 파일 경로: `logs/map_validator.log` (프로젝트 폴더 기준, Git 추적 제외). 최대 5 MiB마다 순환하며 `map_validator.log.1`~`.3`을 보관합니다.
- 작업 스레드의 로그는 Qt 신호를 거쳐 UI에 표시하므로 스레드에서 위젯을 직접 수정하지 않습니다.
- 오류는 가능한 경우 traceback의 **실제 예외 발생 파일과 줄번호**를 기록합니다. traceback은 한 줄 로그 안에 포함합니다.
- `Apply externally defined coinit_flags: 2`는 외부에서 설정된 STA COM 방식을 pywinauto가 받아들였다는 안내 경고로, 동작 실패 자체를 의미하지 않습니다. 경고는 숨기지 않고 `WARNING`으로 기록합니다.
- 로그에는 검수 ID, 작업 파일 경로 등의 정보가 포함될 수 있으므로 외부 공유 전 확인하세요.

## UI 항목과 작업 — 4단계 수동 촬영

- **창 정보 보기**: 실행 중인 창·하위 컨트롤 조회. 업무 창을 이동·확대·복원하지 않습니다.
- **입력 프로그램/로드뷰 프로그램**: 기본 제목 `HD_3D Tool` / `NLadybugSv`. 선택 버튼은 사용자가 명시적으로 누를 때만 해당 창을 전면으로 가져올 수 있으나, **촬영 버튼은 창을 활성화하지 않습니다**. 입력툴은 자동 복원·이동·크기 변경하지 않습니다.
- **검수 ID**: `교차로 선형 검수` 창에서 왼쪽 클릭 후 약 200ms 뒤 선택한 Polygon/Link ID를 별도 스레드로 읽습니다. 선택 ID는 **`config.yaml`에 저장하지 않습니다**. 검수 ID가 바뀌면 해당 결과 폴더의 촬영 상태를 다시 불러옵니다.
- **저장 경로**: `output.directory`를 사용하며, 설정 변경 시 `config.yaml`에 저장하고 기존 설정은 백업합니다.
- **4개의 촬영 버튼**: **진입 전 촬영 / 진입 후 · 좌 촬영 / 진입 후 · 직 촬영 / 진입 후 · 우 촬영**. 사용자가 각 방향으로 화면을 직접 맞춘 다음 해당 버튼을 누릅니다. **도로가 없고 건물이 보이는 방향도 사진을 찍어야 합니다.**
- **촬영 상태**: 미촬영, 촬영 완료(버전 표시), 일부 누락을 구분합니다. 재촬영 시 기존 이미지 이력을 보존하며 새 버전으로 저장합니다. **도로 없음 버튼은 제공하지 않습니다.**
- **촬영본 분석**: 현재 검수 ID에 저장된 네 종류의 두 창 사진 쌍을 읽어 입력툴 기대값과 로드뷰 실제 관측값을 항목별로 비교합니다. 폴더 선택 팝업이나 재촬영은 없습니다. **도로/건물 판독은 초기 후보 수준**이며, 차로 수·화살표·유도선 개수 등 검증되지 않은 값은 판단 보류로 표시합니다.
- **교차로 도로 스코어**: 같은 AI 도로 마스크로 진입 전 **좌·직·우** 각 영역 스코어와, 진입 후 **좌회전/직진/우회전 촬영 사진의 정면** 스코어를 계산합니다. 총 6개 값(0~1)을 UI에 표시하며 전후 차이는 표시하지 않습니다. 모델과 ROI가 동일한 기준이며 스코어 자체는 실제 회전 가능 여부를 의미하지 않습니다.
- **입력툴 도로 후보·선형**: 진입 후 각 단계 입력툴 사진의 색상 경로가 해당 방향으로 연결된 후보일 때 `있음`과 고정 휴리스틱 후보 점수 0.62를 표시합니다. 확률이 아니며, 후보가 불명확하거나 사진이 없으면 판단 보류입니다. 도로 선형의 방향별 표시는 입력툴 도로 존재 후보와 해당 방향 로드뷰 전방 도로 존재 후보를 비교해 P(일치 후보), F(불일치 의심), N(판단 보류)으로 표시합니다. 실제 선형의 형상까지 일치하는지 확인한 결과는 아니며 최종 검수가 필요합니다.
- **분석 중지**: 작업 스레드에 중지를 요청합니다. AI 모델 최초 로딩 및 추론 중에는 즉시 반영되지 않을 수 있습니다.
- **항목별 비교**: 진입 전은 정지선/차로 수/화살표/컬러유도선, 진입 후 좌·직·우는 도로 존재/차로 수/일반 유도선/컬러유도선을 기대값·관측값·검수 상태로 표시합니다.
- **로드뷰 정지선 threshold**: 단계별 촬영 아래에서 기본 `0.68` 값을 `0.35~0.95` 사이로 조절할 수 있습니다. **높일수록 단독 흰색 정지선 검출을 엄격하게 판정**합니다. 변경값은 로컬 `config.yaml`의 `analysis.stop_line_roadview_threshold`에 저장되며 **선택된 Polygon/Link ID는 저장하지 않습니다**.
- **진입 전 정지선 PASS/FAIL/REVIEW**: 입력툴은 **시안색 가로줄**, 로드뷰는 **횡단보도와 구분되는 단독 흰색 정지선**만 확인합니다. 유무가 같으면 `PASS`, 다르면 `FAIL`, 실제 정지선과 횡단보도의 구분이 어렵거나 threshold 미달이면 `검수 필요(REVIEW)`입니다. 흰색/노란색 **횡단보도 자체는 정지선으로 판정하지 않습니다**. 근거 그림과 상세 사유는 `overlays/` 및 `staged_analysis.json`에 보관됩니다.
- **결과 폴더·로그**: 현재 검수 ID 결과 폴더와 앱 로그·로그 복사를 제공합니다.

촬영은 두 프로그램 모두 **WGC(Windows Graphics Capture)**만 사용하며 **`PrintWindow`를 호출하지 않습니다**. HD_3D Tool에서 `PrintWindow`를 사용하면 실제 3D 뷰가 흰색으로 변했던 문제가 있어, WGC 실패 시에도 재시도하지 않습니다. 촬영이나 분석에서 자동 Zoom·W/S 이동·스크롤·로드뷰 열기·창 이동·크기 변경을 하지 않습니다.

현재 4단계 수동 촬영과 기본 비교는 코드에 연결되어 있지만, **Windows 현장 실행과 자동 판독 정확도는 사용자의 단계별 테스트가 필요**합니다. 입력툴/로드뷰의 실제 노면표시 추출 기준은 [4단계 디자인](INTERSECTION_REVIEW_DESIGN.md)과 [요구사항](REQUIREMENTS.md)을 참고하세요.

## 저장 파일과 재촬영

검수 ID에 따라 기존 폴더 내부에 4단계 촬영 파일을 추가합니다. 예를 들어:

~~~text
results/Polygon 480706820- Link 142/
  captures/
    before/
      Polygon 480706820-Link 142_before_HD_3D Tool.png
      Polygon 480706820-Link 142_before_NLadybugSv.png
    after_left/
      ..._after_left_HD_3D Tool.png
      ..._after_left_NLadybugSv.png
    after_straight/
      ...
    after_right/
      ...
  staged_capture.json
  staged_analysis.json
  overlays/
    before_r01_input.png
    before_r01_roadview.png
    ...
  [기존 캡처 원본 및 result.json 유지]
~~~

각 단계의 입력툴/로드뷰 사진 쌍은 동일한 캡처 회차로 묶습니다. **같은 단계 재촬영 시 `_r02`, `_r03` 등 새 버전 파일을 추가**하고 메타데이터의 `history`에 직전 버전을 남깁니다. 분석은 최신 촬영본을 사용하고 `staged_analysis.json`과 `overlays/`에 결과를 저장합니다. 기존 `result.json`과 구버전 PNG는 그대로 유지합니다.

### 비교용 스코어 파일

`촬영본 분석`을 누르면 기존 로드뷰 사진에 대한 AI 도로 마스크를 **추가 모델 실행 없이 재사용**하여 다음 데이터를 저장합니다.

| 구분 | 좌 | 직 | 우 |
|---|---|---|---|
| 진입 전 1장 | 좌 ROI 도로 비율 | 중앙 ROI 도로 비율 | 우 ROI 도로 비율 |
| 진입 후 3장 | 좌회전 사진의 **정면** 비율 | 직진 사진의 **정면** 비율 | 우회전 사진의 **정면** 비율 |

- `<검수 ID>/road_scores.json` — 해당 검수 ID 최신 점수 6개와 시점별 차이.
- `<검수 ID>/score_history/` — 재분석할 때마다 측정 기록을 별도 JSON으로 보존.
- **`<저장 경로>/road_scores.csv`** — 여러 교차로를 한 표로 비교하는 통합 CSV. 검수 ID당 최신 한 행만 유지. UTF-8 BOM 인코딩.
- `staged_analysis.json` — 기존 분석 결과 안에도 동일 스코어 포함.
- `null`(미측정)은 CSV 공란으로, 0(해당 영역의 도로 픽셀이 0개)은 0으로 보관합니다.

스코어는 화면에서 **해당 영역을 road로 분할한 픽셀 비율(0~1)**이며, 추후 실무 판정·통계 비교를 위한 기초 자료입니다. 전·후는 촬영 위치가 다르므로 수치 차이만으로 실제 도로 불일치를 확정할 수 없습니다. 자세한 ROI, 열 이름 및 모델 버전은 [검수 디자인](INTERSECTION_REVIEW_DESIGN.md)에 명시했습니다.

한 단계만 촬영되었어도 그 단계의 **부분 분석은 허용**합니다. 사진을 찍지 않은 방향을 ‘도로 없음’으로 간주하지 않으며, 건물이 화면에 있다고 무조건 ‘불일치’로 판정하지 않습니다. **입력툴이 해당 진출 도로를 예상하고 로드뷰 전방 중앙에 건물 영역이 우세하고 도로가 거의 없을 때** 불일치 **의심**으로 표시합니다. 사용자 사진으로 임계값과 예외 기준을 보정합니다.

## Windows 비활성 캡처 확인

1. `HD_3D Tool`과 `NLadybugSv` 창을 사용자가 직접 정상 상태로 띄웁니다(최소화하지 않음).
2. 교차로 진입 전 또는 좌·직·우 중 한 방향으로 **사용자가 직접 로드뷰를 맞춥니다**.
3. map_validator에서 해당 단계 촬영 버튼을 누릅니다. 포그라운드가 다른 프로그램이어도 WGC로 두 창을 읽도록 설계했습니다.
4. `logs/map_validator.log`에서 `WGC 비활성 창 캡처 성공` 기록을 확인하고, 현재 검수 ID의 `captures/<stage>/`에서 두 원본을 확인합니다.
5. 실제 화면이 흰색·검은색으로 바뀌거나 사진이 비정상이라면 재촬영 전에 로그와 현재 프로그램 상태를 확인합니다.

**실환경 동작 여부와 분석 정확도는 사용자 Windows PC에서 단계별 검수가 필요합니다.**

## 검수 방식과 안전

**모든 촬영 단계는 사용자가 직접 시점과 방향을 정합니다.** UI는 WGC 비활성 캡처와 저장된 사진 분석만 수행합니다. AI 모델은 도로·건물의 의미 영역과 일부 노면표시 후보를 제공하고, 정확한 차로 수·복합 화살표·유도선 개수 등은 충분한 근거가 없으면 `null`/판단 보류로 보존합니다.

- 비교 결과 `match_candidate`는 일치 확정이 아닌 **일치 후보**입니다.
- `mismatch_review`도 사진 방향·지도 데이터·인식 오류를 확인해야 하는 **불일치 의심**입니다.
- `insufficient_evidence`는 사진 누락·미인식·모델 한계 때문에 판단 불가 상태입니다.
- **검수 ID는 메모리에서만 갱신**하고 `config.yaml`에는 보관하지 않습니다.
- 실무 사진·촬영 폴더·검수 결과를 GitHub에 업로드하지 않습니다.
- 현장 테스트에서 새 요구사항이 발견되면 `REQUIREMENTS.md`에 반영하고 컨셉에 해당하는 내용은 `PROJECT_CONCEPT.md`도 업데이트합니다.

AI와 Windows 제어 로직은 UI 스레드를 막지 않도록 분리합니다. 최종 업무 판정·승인은 사용자가 합니다.

## 알려진 제약

사용자 확인으로 입력도구 WGC 캡처는 정상 동작하지만, **로드뷰 WGC 캡처는 실제 업무 Windows 환경에서 별도 확인이 필요합니다.** 창 제목·버튼 템플릿은 환경에 맞게 설정해야 합니다. 두 프로그램 모두 WGC만 사용하며 프레임이 비어 있거나 캡처에 실패해도 `PrintWindow`로 폴백하지 않습니다. 창을 최소화하거나 Windows 세션이 잠긴 경우 캡처가 실패할 수 있습니다. AI 모델 최초 다운로드에는 네트워크와 저장 공간이 필요할 수 있습니다.
### 선택 조회 지연 진단 로그

교차로 창 클릭 이후 선택 조회 시작 시 클릭 후 경과 시간과 Win32 창 목록·트리 조회 및 필요한 경우 UI Automation 창·트리 조회의 시작/종료와 소요 시간을 작업 로그에 남긴다. 조회 결과와 전체 소요 시간도 기록하며 조회 도중 멈춘 경우 마지막 시작 로그로 단계를 확인할 수 있다. 클릭 후크 안에서는 로그를 기록하지 않는다. 이 시간은 지연 원인을 확인하기 위한 자료이며 원인 확정이나 성능 개선을 의미하지 않는다.

### 선택 자동 감시 비교

`교차로 선택 자동 감시`는 실행 시 켜져 있으며, 끄면 전역 마우스 후크를 해제하고 검수 ID 자동 갱신을 중지한다. 후크 해제 완료 로그를 확인한 뒤 다른 창에서 드래그 반응을 비교할 수 있다. 다시 켜면 감시가 재시작되며 다음 선택 시 ID가 갱신된다. 전환 시 오래된 ID의 오사용을 막기 위해 입력된 검수 ID를 비운다. 끈 상태에서는 ID를 직접 입력할 수 있고 빈 상태에서 촬영·분석을 시작하면 기존 방식대로 선택값을 한 번 조회한다. 진행 중인 조회가 즉시 종료되지 않을 수 있으며 이때 경고 로그를 남긴다. 자동 감시 설정은 재실행 시 기본 켜짐이다.

### 활성 창에서만 선택 감시

자동 감시가 켜져 있으면 Windows 활성 창 변경 이벤트를 감지하고 교차로 선형 검수창이 활성화된 동안에만 전역 마우스 후크를 등록한다. 다른 창으로 전환하면 후크를 해제한다. 검수창을 활성화한 클릭이 등록 전에 발생할 수 있으므로 활성화 시 선택값 조회를 한 번 예약하고, 이후 클릭 시에도 기존 지연 조회를 수행한다. 감시를 끄면 활성 창 이벤트와 마우스 후크를 모두 해제한다. 실제 드래그 반응과 선택 ID 갱신은 Windows 현장에서 확인해야 한다.

### 촬영·분석 결과 스크롤

단계별 촬영 시 촬영 버튼과 결과 내용 갱신으로 항목별 비교 결과로 자동 이동하지 않으며 현재 스크롤 위치를 유지한다. 촬영본 분석 결과가 도착하면 항목별 비교 결과 영역으로 이동하고 결과 텍스트는 처음부터 보여준다. 분석 실패나 중지 시에는 결과로 자동 이동하지 않는다. 이 동작은 제어창의 스크롤에만 적용하며 대상 프로그램 창은 조작하지 않는다.

- 검수 이미지에서 GUIDE ROI가 지나치게 넓고 **HDL View 글자 하단(Y)부터 아래쪽까지** 이어져 차량 앞쪽 유도선 위치를 충분히 포함하지 못했다. 검수자가 분홍색으로 표시한 형태처럼 **현재 위치 빨간 사각형을 아래쪽 기준점**으로 삼고, 도면 위쪽으로 긴 세로 ROI를 배치한다.
- GUIDE ROI는 빨간 현재 위치 `point`와 검은 도면 경계 `canvas_bounds`로 독립 계산한다. **좌우 반폭 도면 너비의 18%(최소 55px), 위쪽 도면 높이 65%(최소 45px), 아래쪽 4%(최소 16px)**이며 도면 경계에 맞춰 자른다. 현재 위치가 유효하지 않으면 임의의 영역을 만들지 않는다. 빨간 현재 위치 표시점 주변의 상단 도면까지 포함할 수 있고, **STOP ROI의 상단 및 HDL View 글자 하단으로 GUIDE ROI 상단을 제한하지 않는다.**
- `GUIDE ROI` 자주색 테두리, U# 후보·원본 RGB(0,128,255)·8연결 그룹화는 유지한다. 결과 `checks.guidance_lines.roi`와 `roi_rules.positioning=vehicle_position_to_canvas_top`, `position_point_px`, `canvas_bounds`에 계산 기준을 기록한다.
- `STOP ROI`의 S/G/C/A/W와 `PATH ROI`의 P#는 **이번 변경에서 범위·기준을 수정하지 않는다**. WGC 수동 촬영 및 기존 원본 PNG·JSON 이력은 보존한다. Windows 실환경에서 ROI 크기/유도선 포함률은 별도 현장 확인이 필요하며 테스트 코드는 추가·실행하지 않았다.

## 2026-11-17 STOP ROI 축소 및 노면화살표 검출 범위 동일화

- 빨간 차량 현재 위치 `point`와 실제 검은 도면 `canvas_bounds` 기준으로 `STOP ROI`를 작게 계산한다. 좌우 반폭 도면 너비의 **18%**(최소 55px), 위쪽 도면 높이의 **25%**(최소 45px), 아래쪽 도면 높이의 **10%**(최소 35px). `blue_markings.stop_roi`에서 조정할 수 있으며 도면 경계를 넘지 않는다.
- **정지선 S#/G#와 노면화살표 A#는 같은 `checks.stop_line.roi` 좌표를 공유**한다. 기존 `local_road_arrow_candidates(..., roi=stop_line.get("roi"))`를 유지하여 화살표가 작은 STOP ROI 밖에서 검출되지 않도록 했다. 화살표 색상·회색 사각형·초록 테두리·흰색 제외 로직은 수정하지 않았다.
- 이전 넓은 검출 영역(HDL View/Input 글자 하단+10px 상단, 좌우 이미지 너비 31%, 현재위치 아래 이미지 높이 44%)은 `checks.stop_line.context_roi`로 분리했다. **중앙선 C, 흰선 W, 진입 경로선 P**는 이 넓은 영역을 계속 사용한다. GUIDE ROI(U)는 독립적으로 위쪽 탐색을 계속한다. 텍스트 기준이 확인되지 않으면 LINE 및 P 분석만 보류하고, STOP·A는 빨간 차량 위치가 검출되면 수행한다.
- 근거 이미지에 작은 주황색 `STOP ROI`(S/G·A)와 옅은 회색 `LINE ROI`(C/W/P) 테두리를 각각 표시한다. `review_regions`도 실제 분석 범위와 일치시킨다. 기존 WGC 원본·촬영 이력은 보존하고 새 분석 결과만 갱신한다.
- **현장 미검증:** 차량 위치가 교차로에 가까운 정도에 따라 STOP/A 후보가 작은 범위에서 누락될 수 있다. Windows 현장 분석과 자동 테스트는 요청받지 않아 실행하지 않았다.

## 2026-11-17 GUIDE/STOP/PATH ROI 위치 재설정 · LINE ROI 제거

- GUIDE ROI: 빨간 현재 위치 위쪽 교차로를 탐색하되, **차량 앞쪽 가장 가까운 시안색 정지선 후보 선분 위치까지 하단을 내린다**(4px 여유). 선분이 발견되지 않으면 현재 위치를 임시 기준으로 사용하고 `stop_line_reference.status`에서 `cyan_segment_candidate`와 `vehicle_position_fallback`을 구분한다. 시안색 후보는 실제 정지선으로 자동 확정하지 않는다.
- STOP ROI: **GUIDE ROI의 상단부터 전체 높이 70% 지점**까지 상단을 올리고, 하단은 현재 위치 아래 기존 10%를 유지한다. 정지선 S/G와 화살표 A는 같은 STOP ROI를 공유한다.
- PATH ROI: 현재 위치 빨간 마커를 아래쪽 기준점으로 삼아 **도면 높이 45% 위쪽**을 탐색한다. 마커 아래로는 4px 여유만 두며 도면 경계 밖으로 확장하지 않는다.
- **LINE ROI 삭제:** 회색 사각형과 'LINE ROI' 라벨, 별도의 context_roi 결과 및 UI 안내를 제거한다. 중앙선 C와 흰선 W는 세 ROI를 포함하는 내부 직사각형 탐색 범위(`candidate_search_bounds`)에서 계속 검출하되 **네 번째 테두리를 그리지 않는다**. C/W의 `review_regions.border`는 `none`이다.
- `blue_markings.guidance_roi/stop_roi/approach_roi` 수치를 갱신했고 ROI 3종(자주/주황/연파랑)은 유지한다. 기존 WGC 원본·검수 이력 보존. Windows 실환경 및 자동 테스트는 요청받지 않아 실행하지 않았다.

## 2026-11-17 ROI 오해 정정: 모두 현재 위치 기준으로 독립 계산

- **최신 확정 기준:** GUIDE, STOP, PATH의 상단/하단은 모두 **빨간 현재 위치 표시점 `red_marker.point`**의 화면 Y좌표에서 도면 높이의 고정 비율 또는 고정 px만큼 위아래로 이동하여 산정한다. ROI끼리 좌표를 참조하거나 먼저 검출된 시안색 선분을 ROI 경계로 사용하지 않는다. 위 2026-11-17 'GUIDE/STOP/PATH ROI 위치 재설정'에 기록된 **`stop_line_reference` 및 GUIDE 높이에 의존하는 STOP 상단 계산은 폐기**한다.
- 공통 `canvas_bounds`는 영상 도면의 클리핑과 비율 크기 계산에만 사용한다. `GUIDE ROI`: 위 65%, 아래 4%, 좌우 반폭 도면 너비 18%. `STOP ROI`: 위 **45.5%**, 아래 10%, 좌우 반폭 18%. 이 45.5%는 이전 GUIDE 상방 높이 65%의 **약 70%에 해당하는 고정 크기**라는 뜻이며 실제 GUIDE ROI 좌표와 무관하다. `PATH ROI`: 위 45%, 아래 4px, 좌우 반폭 30%. 작은 도면에서 각 `min_*_px` 기준을 적용한다.
- `map_validator/analysis/input_tool/local_stop_line.py`에서 `detect_stop_line_reference`를 삭제하고 `guide_roi`, `stop_reference` 인수와 연결된 계산을 제거한다. `local_guidance_line.py`에서도 `stop_line_y`, `stop_reference` 인수를 제거한다. `individual_capture.py`는 동일한 `point`와 `canvas_bounds`를 세 검출기에 각각 전달한다. JSON의 `stop_line_reference` 최상위 필드는 새 분석 결과에서 제거하며, 검사 목적 외부 원본 PNG와 이전 분석 이력은 보존한다.
- 기존 S/G 및 A 공통 STOP ROI, U GUIDE, P PATH, C/W의 내부 후보 검출(`candidate_search_bounds`)은 유지한다. LINE ROI 테두리는 복구하지 않는다. 또한 정지선 검출의 선 길이 계산에서 이미지 크기 변수의 기존 불일치(`height,width` 미정의)를 `h,w`로 바로잡는다.
- **검증 상태:** 원격 소스·호출 관계 정적 확인만 실시. Windows 현장 실행·자동 테스트 및 테스트 코드 추가는 요청받지 않아 수행하지 않았다.


## 2026-11-17 중앙선 그룹화 값 직접 조정 (설정 ⚙)

- 상단 **⚙ 분석 설정** 창에 기존 로드뷰 정지선 threshold와 별도로 **입력툴 노란 중앙선 2차 그룹화** 항목 3개를 제공한다.
- **1차(기존 고정 분석):** 원본 Y 선분을 기울기 8°, 수직거리 5px, 연결 간격 12px로 묶어 `CG#` 그룹을 만든다. 설정을 바꿔도 1차 결과는 유지한다.
- **2차(설정값 적용):** 1차 `CG#` 그룹의 대표 선분끼리 다시 기울기·수직거리·연결 간격을 비교하고 병합해 최종 `C#`를 만든다. 기울기 0~30°(기본 8°), 거리 0~30px(기본 5px), 연결 0~120px(기본 12px)를 조정할 수 있다. 2차에서는 1차 그룹을 분할할 수 없다.
- 저장하면 로컬 `config.yaml`의 `analysis.center_line_grouping`에 기록된다. 저장만으로 기존 근거 이미지가 자동 갱신되지는 않으며 **정지선 분석을 다시 눌러야** 새 2차 값이 적용된다. 원본 PNG는 유지한다.
- JSON `checks.center_line`에 `first_pass_line_groups`, `first_pass_group_count`, `second_pass_group_count`, 최종 `line_groups` 및 `grouping_rules.first_pass/second_pass`를 남긴다. 상세 화면은 1차→2차 후보 수와 구성 관계를 보여준다. 정지선 S/G 및 흰선 W에는 영향이 없다. 중앙선 여부·개수는 사람이 최종 검수한다.

### 2026-11-17 2차 끝점 연결·반복 병합 및 상세 비교 로그 (현행)

- **1차 Y→CG 분석은 8°/5px/12px 고정**으로 유지한다. 2차 CG→C는 기울기 차이, 연장선 수직 편차, 두 CG의 시작·종료 끝점 XY 직선거리를 기준으로 연결 가능한 끝점 쌍을 탐색한다. 크게 중첩된 평행선은 제외하며 동일 끝점을 중복 사용하지 않는다.
- 연결 가능한 CG 쌍을 가까운 순으로 연결하고 Union-Find로 연쇄 병합한다. 1차 그룹 및 원본 Y 조각은 유지한다.
- 기존 `analysis.center_line_grouping.max_gap_px` 설정 키는 호환 유지하되 2차에서 **끝점 연결 거리(px)**로 해석한다. 기본 20px, 최대 300px이며 저장된 이전 값(예: 120px)은 초기화하지 않는다. 기울기 기본 8°(최대 30°), 수직거리 기본 5px(최대 30px) 유지.
- 분석 결과 `checks.center_line.second_pass_diagnostics.pair_comparisons`에는 **비교한 모든 CG 쌍의 좌표, 끝점 직선거리, 기울기 차이, 수직거리, 각 허용값, PASS/FAIL, 제외 사유, 최종 C 그룹**을 남긴다. `accepted_connections`, `rejected_pairs_by_reason` 등 요약도 기록한다.
- 작업 로그에는 전체 집계, 모든 PASS 및 **가장 가까운 FAIL 20쌍**을 기록하고, UI 결과 상세에는 PASS 및 가까운 FAIL 15쌍을 표시한다. 전체 비교는 분석 JSON에서 확인한다. '정지선 분석'을 다시 실행해야 새 설정을 반영한다.
- 정지선 S/G 및 흰색 W 후보 로직은 변경하지 않는다. JSON PASS/FAIL은 **선 조각의 연결 적합성**만 뜻하며 도로 검수 승인 판정이 아니다. Windows 현장 이미지 분석과 자동 테스트는 요청받지 않아 미실행이다.
