# map_validator Windows 제어 UI

참고 UI: https://github.com/bluehawhy/nv_c_test (PyQt6, 작은 반투명 상단 고정창, 드래그 헤더, 상태·로그 표시).

## 실행 조건 및 설치

Windows 11과 설치된 호환 Python을 사용합니다. 3.11이 꼭 필요하지는 않습니다. Python 런처에서 사용할 수 있는 버전은 `py list`로 확인합니다.

```powershell
git clone https://github.com/bluehawhy/map_validator.git
cd map_validator
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements-ui.txt
# AI 분석 시에만 추가 설치
python -m pip install -r requirements-ai.txt
python -m UI
```

`python -m UI` 실행 시에는 PyQt6·pywinauto를 불러오기 전에 메인 스레드 COM 모드를 STA로 지정합니다. 이는 COM 모드 충돌 시 MTA에서 STA로 재시도하는 경고의 원인을 줄이며, 경고 메시지 자체를 숨기지는 않습니다. pywinauto 버전에 따라 명시된 COM 설정을 안내하는 별도 메시지는 나올 수 있습니다.

기존 설치 환경에서 업데이트할 때도 **`python -m pip install -r requirements-ui.txt`를 다시 실행**해 주세요. 입력도구와 로드뷰 모두 `windows-capture>=2.0.1`을 통한 WGC(Windows Graphics Capture)로 촬영합니다.

또는 `UI\run_ui.bat`을 실행합니다. 실행할 때 `config.yaml`에 없는 항목만 `config.example.yaml`에서 추가하고, 기존에 들어 있는 항목과 값은 그대로 유지한 뒤 UI를 엽니다. `config.yaml`이 없으면 예제 설정으로 새로 만듭니다.

## 앱 로그

앱 시작, 창 검색, Polygon/Link 선택, 화면 준비, 캡처, 분석, 오류 및 Python 경고를 다음 구조로 표시·저장합니다.

`로그타입 | 날짜 시간 | 코드파일:줄번호 | 로그 텍스트`

예시 (파일명·줄번호는 실제 발생 위치에 따라 달라집니다):

```text
INFO | 2026-11-04 10:55:40.123 | UI/app.py:563 | 시작: analyze / Polygon 480706169- Link 98
WARNING | 2026-11-04 10:55:40.456 | pywinauto/__init__.py:71 | UserWarning: Apply externally defined coinit_flags: 2
ERROR | 2026-11-04 10:55:40.789 | map_validator/windows.py:142 | 작업 오류: zoom label was not exposed through Windows UI Automation | traceback: ...
```

- UI의 **작업 로그** 영역과 콘솔에서 동일 형식을 확인할 수 있습니다. **로그 복사**는 표시된 로그를 복사하며, **로그 폴더**는 저장된 로그 파일 위치를 엽니다.
- 파일 경로: `logs/map_validator.log` (프로젝트 폴더 기준, Git 추적 제외). 최대 5 MiB마다 순환하며 `map_validator.log.1`~`.3`을 보관합니다.
- 작업 스레드의 로그는 Qt 신호를 거쳐 UI에 표시하므로 스레드에서 위젯을 직접 수정하지 않습니다.
- 오류는 가능한 경우 traceback의 **실제 예외 발생 파일과 줄번호**를 기록합니다. traceback은 한 줄 로그 안에 포함합니다.
- `Apply externally defined coinit_flags: 2`는 외부에서 설정된 STA COM 방식을 pywinauto가 받아들였다는 안내 경고로, 동작 실패 자체를 의미하지 않습니다. 경고는 숨기지 않고 `WARNING`으로 기록합니다.
- 로그에는 검수 ID, 작업 파일 경로 등의 정보가 포함될 수 있으므로 외부 공유 전 확인하세요.

## UI 항목과 작업 — 4단계 수동 촬영

- **창 정보 보기**: 실행 중인 창·하위 컨트롤 조회. 업무 창을 이동·확대·복원하지 않습니다.
- **입력 프로그램/로드뷰 프로그램**: 기본 제목 `HD_3D Tool` / `NLadybugSv`. 선택 버튼은 사용자가 명시적으로 누를 때만 해당 창을 전면으로 가져올 수 있으나, **촬영 버튼은 창을 활성화하지 않습니다**. 입력툴은 자동 복원·이동·크기 변경하지 않습니다.
- **검수 ID**: `교차로 선형 검수` 창에서 왼쪽 클릭 후 약 200ms 뒤 선택한 Polygon/Link ID를 별도 스레드로 읽습니다. 선택 ID는 **`config.yaml`에 저장하지 않습니다**. 검수 ID가 바뀌면 해당 결과 폴더의 촬영 상태를 다시 불러옵니다.
- **저장 경로**: `output.directory`를 사용하며, 설정 변경 시 `config.yaml`에 저장하고 기존 설정은 백업합니다.
- **4개의 촬영 버튼**: **진입 전 촬영 / 진입 후 · 좌 촬영 / 진입 후 · 직 촬영 / 진입 후 · 우 촬영**. 사용자가 각 방향으로 화면을 직접 맞춘 다음 해당 버튼을 누릅니다. **도로가 없고 건물이 보이는 방향도 사진을 찍어야 합니다.**
- **촬영 상태**: 미촬영, 촬영 완료(버전 표시), 일부 누락을 구분합니다. 재촬영 시 기존 이미지 이력을 보존하며 새 버전으로 저장합니다. **도로 없음 버튼은 제공하지 않습니다.**
- **촬영본 분석**: 현재 검수 ID에 저장된 네 종류의 두 창 사진 쌍을 읽어 입력툴 기대값과 로드뷰 실제 관측값을 항목별로 비교합니다. 폴더 선택 팝업이나 재촬영은 없습니다. **도로/건물 판독은 초기 후보 수준**이며, 차로 수·화살표·유도선 개수 등 검증되지 않은 값은 판단 보류로 표시합니다.
- **교차로 도로 스코어**: 같은 AI 도로 마스크로 진입 전 **좌·직·우** 각 영역 스코어와, 진입 후 **좌회전/직진/우회전 촬영 사진의 정면** 스코어를 계산합니다. 총 6개 값(0~1)을 UI에 표시하며 전후 차이는 표시하지 않습니다. 모델과 ROI가 동일한 기준이며 스코어 자체는 실제 회전 가능 여부를 의미하지 않습니다.
- **입력툴 도로 후보·선형**: 진입 후 각 단계 입력툴 사진의 색상 경로가 해당 방향으로 연결된 후보일 때 `있음`과 고정 휴리스틱 후보 점수 0.62를 표시합니다. 확률이 아니며, 후보가 불명확하거나 사진이 없으면 판단 보류입니다. 색상 선형 회전각은 후보로만 표시하고 P/F/PA 등 코드 문자는 아직 판독하지 못합니다.
- **분석 중지**: 작업 스레드에 중지를 요청합니다. AI 모델 최초 로딩 및 추론 중에는 즉시 반영되지 않을 수 있습니다.
- **항목별 비교**: 진입 전은 정지선/차로 수/화살표/컬러유도선, 진입 후 좌·직·우는 도로 존재/차로 수/일반 유도선/컬러유도선을 기대값·관측값·검수 상태로 표시합니다.
- **로드뷰 정지선 threshold**: 단계별 촬영 아래에서 기본 `0.68` 값을 `0.35~0.95` 사이로 조절할 수 있습니다. **높일수록 단독 흰색 정지선 검출을 엄격하게 판정**합니다. 변경값은 로컬 `config.yaml`의 `analysis.stop_line_roadview_threshold`에 저장되며 **선택된 Polygon/Link ID는 저장하지 않습니다**.
- **진입 전 정지선 PASS/FAIL/REVIEW**: 입력툴은 **시안색 가로줄**, 로드뷰는 **횡단보도와 구분되는 단독 흰색 정지선**만 확인합니다. 유무가 같으면 `PASS`, 다르면 `FAIL`, 실제 정지선과 횡단보도의 구분이 어렵거나 threshold 미달이면 `검수 필요(REVIEW)`입니다. 흰색/노란색 **횡단보도 자체는 정지선으로 판정하지 않습니다**. 근거 그림과 상세 사유는 `overlays/` 및 `staged_analysis.json`에 보관됩니다.
- **결과 폴더·로그**: 현재 검수 ID 결과 폴더와 앱 로그·로그 복사를 제공합니다.

촬영은 두 프로그램 모두 **WGC(Windows Graphics Capture)**만 사용하며 **`PrintWindow`를 호출하지 않습니다**. HD_3D Tool에서 `PrintWindow`를 사용하면 실제 3D 뷰가 흰색으로 변했던 문제가 있어, WGC 실패 시에도 재시도하지 않습니다. 촬영이나 분석에서 자동 Zoom·W/S 이동·스크롤·로드뷰 열기·창 이동·크기 변경을 하지 않습니다.

현재 4단계 수동 촬영과 기본 비교는 코드에 연결되어 있지만, **Windows 현장 실행과 자동 판독 정확도는 사용자의 단계별 테스트가 필요**합니다. 입력툴/로드뷰의 실제 노면표시 추출 기준은 [4단계 디자인](INTERSECTION_REVIEW_DESIGN.md)과 [요구사항](REQUIREMENTS.md)을 참고하세요.

## 저장 파일과 재촬영

검수 ID에 따라 기존 폴더 내부에 4단계 촬영 파일을 추가합니다. 예를 들어:

~~~text
results/Polygon 480706820- Link 142/
  captures/
    before/
      Polygon 480706820-Link 142_before_HD_3D Tool.png
      Polygon 480706820-Link 142_before_NLadybugSv.png
    after_left/
      ..._after_left_HD_3D Tool.png
      ..._after_left_NLadybugSv.png
    after_straight/
      ...
    after_right/
      ...
  staged_capture.json
  staged_analysis.json
  overlays/
    before_r01_input.png
    before_r01_roadview.png
    ...
  [기존 캡처 원본 및 result.json 유지]
~~~

각 단계의 입력툴/로드뷰 사진 쌍은 동일한 캡처 회차로 묶습니다. **같은 단계 재촬영 시 `_r02`, `_r03` 등 새 버전 파일을 추가**하고 메타데이터의 `history`에 직전 버전을 남깁니다. 분석은 최신 촬영본을 사용하고 `staged_analysis.json`과 `overlays/`에 결과를 저장합니다. 기존 `result.json`과 구버전 PNG는 그대로 유지합니다.

### 비교용 스코어 파일

`촬영본 분석`을 누르면 기존 로드뷰 사진에 대한 AI 도로 마스크를 **추가 모델 실행 없이 재사용**하여 다음 데이터를 저장합니다.

| 구분 | 좌 | 직 | 우 |
|---|---|---|---|
| 진입 전 1장 | 좌 ROI 도로 비율 | 중앙 ROI 도로 비율 | 우 ROI 도로 비율 |
| 진입 후 3장 | 좌회전 사진의 **정면** 비율 | 직진 사진의 **정면** 비율 | 우회전 사진의 **정면** 비율 |

- `<검수 ID>/road_scores.json` — 해당 검수 ID 최신 점수 6개와 시점별 차이.
- `<검수 ID>/score_history/` — 재분석할 때마다 측정 기록을 별도 JSON으로 보존.
- **`<저장 경로>/road_scores.csv`** — 여러 교차로를 한 표로 비교하는 통합 CSV. 검수 ID당 최신 한 행만 유지. UTF-8 BOM 인코딩.
- `staged_analysis.json` — 기존 분석 결과 안에도 동일 스코어 포함.
- `null`(미측정)은 CSV 공란으로, 0(해당 영역의 도로 픽셀이 0개)은 0으로 보관합니다.

스코어는 화면에서 **해당 영역을 road로 분할한 픽셀 비율(0~1)**이며, 추후 실무 판정·통계 비교를 위한 기초 자료입니다. 전·후는 촬영 위치가 다르므로 수치 차이만으로 실제 도로 불일치를 확정할 수 없습니다. 자세한 ROI, 열 이름 및 모델 버전은 [검수 디자인](INTERSECTION_REVIEW_DESIGN.md)에 명시했습니다.

한 단계만 촬영되었어도 그 단계의 **부분 분석은 허용**합니다. 사진을 찍지 않은 방향을 ‘도로 없음’으로 간주하지 않으며, 건물이 화면에 있다고 무조건 ‘불일치’로 판정하지 않습니다. **입력툴이 해당 진출 도로를 예상하고 로드뷰 전방 중앙에 건물 영역이 우세하고 도로가 거의 없을 때** 불일치 **의심**으로 표시합니다. 사용자 사진으로 임계값과 예외 기준을 보정합니다.

## Windows 비활성 캡처 확인

1. `HD_3D Tool`과 `NLadybugSv` 창을 사용자가 직접 정상 상태로 띄웁니다(최소화하지 않음).
2. 교차로 진입 전 또는 좌·직·우 중 한 방향으로 **사용자가 직접 로드뷰를 맞춥니다**.
3. map_validator에서 해당 단계 촬영 버튼을 누릅니다. 포그라운드가 다른 프로그램이어도 WGC로 두 창을 읽도록 설계했습니다.
4. `logs/map_validator.log`에서 `WGC 비활성 창 캡처 성공` 기록을 확인하고, 현재 검수 ID의 `captures/<stage>/`에서 두 원본을 확인합니다.
5. 실제 화면이 흰색·검은색으로 바뀌거나 사진이 비정상이라면 재촬영 전에 로그와 현재 프로그램 상태를 확인합니다.

**실환경 동작 여부와 분석 정확도는 사용자 Windows PC에서 단계별 검수가 필요합니다.**

## 검수 방식과 안전

**모든 촬영 단계는 사용자가 직접 시점과 방향을 정합니다.** UI는 WGC 비활성 캡처와 저장된 사진 분석만 수행합니다. AI 모델은 도로·건물의 의미 영역과 일부 노면표시 후보를 제공하고, 정확한 차로 수·복합 화살표·유도선 개수 등은 충분한 근거가 없으면 `null`/판단 보류로 보존합니다.

- 비교 결과 `match_candidate`는 일치 확정이 아닌 **일치 후보**입니다.
- `mismatch_review`도 사진 방향·지도 데이터·인식 오류를 확인해야 하는 **불일치 의심**입니다.
- `insufficient_evidence`는 사진 누락·미인식·모델 한계 때문에 판단 불가 상태입니다.
- **검수 ID는 메모리에서만 갱신**하고 `config.yaml`에는 보관하지 않습니다.
- 실무 사진·촬영 폴더·검수 결과를 GitHub에 업로드하지 않습니다.
- 현장 테스트에서 새 요구사항이 발견되면 `REQUIREMENTS.md`에 반영하고 컨셉에 해당하는 내용은 `PROJECT_CONCEPT.md`도 업데이트합니다.

AI와 Windows 제어 로직은 UI 스레드를 막지 않도록 분리합니다. 최종 업무 판정·승인은 사용자가 합니다.

## 알려진 제약

사용자 확인으로 입력도구 WGC 캡처는 정상 동작하지만, **로드뷰 WGC 캡처는 실제 업무 Windows 환경에서 별도 확인이 필요합니다.** 창 제목·버튼 템플릿은 환경에 맞게 설정해야 합니다. 두 프로그램 모두 WGC만 사용하며 프레임이 비어 있거나 캡처에 실패해도 `PrintWindow`로 폴백하지 않습니다. 창을 최소화하거나 Windows 세션이 잠긴 경우 캡처가 실패할 수 있습니다. AI 모델 최초 다운로드에는 네트워크와 저장 공간이 필요할 수 있습니다.
