# 프로젝트 컨셉 — map_validator

> 상태: **수동 4단계 촬영·기초 후보 비교 구현 / 현장 검증 및 정밀 판독 보완 중**  
> 기준: 2026-11-04  
> 관련 문서: [교차로 4단계 촬영·검수 UI 디자인](INTERSECTION_REVIEW_DESIGN.md), [기존 선형 후보 비교](LINE_GEOMETRY.md), [요구사항](REQUIREMENTS.md)

## 1. 목적

**map_validator**는 Windows의 **HD_3D Tool(입력툴)**에 등록된 교차로 도로 정보와 **NLadybugSv(로드뷰)**에서 실제 보이는 도로 표시가 일치하는지 검수하도록 돕는 로컬 데스크톱 도구다.

검수자가 교차로와 촬영 위치·시점을 직접 결정하고, 프로그램은 해당 검수 ID의 **입력툴 화면과 로드뷰 화면을 함께 캡처·보관**한다. 이후 사진에서 도로 표지·차로·선형을 인식해 항목별 차이를 표시한다. **자동 판정은 검수 보조 수단이며 최종 결정과 업무 프로그램의 실제 데이터 수정은 사용자 책임**이다.

핵심은 단순히 좌회전·우회전 도로 후보를 찾는 것이 아니라 **입력툴이 제공하는 교차로 진입 전·후 정보와 로드뷰에서 관찰되는 실제 정보를 같은 단계·같은 항목끼리 비교**하는 것이다.

## 2. 검수 단위

- 검수 ID: 기존 교차로 선형 검수 UI에서 선택된 **Polygon ID - Link ID** 기반. Polygon만 선택되면 Polygon ID만 사용한다.
- 검수 데이터는 `output.directory/<검수 ID>/` 아래 보관한다.
- 현재 선택 ID는 UI 메모리에서 갱신한다. **`config.yaml`에 선택 Polygon/Link ID를 저장하지 않는다.**
- 촬영 단위: **단계(stage) × 입력툴/로드뷰 한 쌍의 스크린샷**.
- 검수 단계는 네 종류이며 기본 표시 순서는 **진입 전 → 진입 후 좌 → 진입 후 직 → 진입 후 우**다.

| 단계 코드 | UI 표시 | 사용자가 촬영하는 내용 |
|---|---|---|
| `before` | 교차로 진입 전 | 진입 전 차로·정지선·화살표·컬러유도선이 보이는 시점 |
| `after_left` | 진입 후 · 좌 | 좌측 진행 방향의 실제 도로와 연결 차로가 보이는 시점 |
| `after_straight` | 진입 후 · 직 | 직진 방향의 실제 도로와 연결 차로가 보이는 시점 |
| `after_right` | 진입 후 · 우 | 우측 진행 방향의 실제 도로와 연결 차로가 보이는 시점 |

**촬영 시점·이동·각도 조정은 전적으로 사용자가 수행한다.** 검수 프로그램은 촬영 버튼을 눌렀을 때 현재 열린 두 창을 그대로 WGC(Windows Graphics Capture)로 캡처한다. 자동 W/S 이동, 화면 회전, Zoom 설정, 창 크기·위치 변경 및 자동 복원은 촬영 흐름에 포함하지 않는다.

**방향별 도로가 없어도 좌·직·우 3개 방향 모두 사용자가 반드시 촬영한다.** 프로그램은 로드뷰 사진에서 도로 영역과 건물 등 비도로 영역을 분석해, 입력툴상 예상 진출 도로와 비교한다. 기대 도로가 있는데 실제 촬영 방향이 건물 등으로 막혀 있는 정황이면 **불일치 의심**을 표시한다. 미촬영·사진 불명확·실제 도로 없음은 각각 별개로 처리하며, 자동 판단은 현장 테스트에 따라 지속적으로 보정한다.

## 3. 진입 전 검수 항목

| 항목 | 입력툴의 기대 정보 | 로드뷰에서 확인할 정보 |
|---|---|---|
| 정지선 유무 | 입력툴 화면의 **시안색 가로선**을 정지선 후보로 인식 | 실제 노면 정지선 존재 여부 |
| 진입 전 차로 수 | 입력툴이 나타내는 진입 차로 수 | 실제 진입 차로 수 |
| 차로별 방향 화살표 | 좌·직·우 및 조합 표시(좌직·직우 등) | 실제 노면 화살표의 위치·방향·조합 |
| 컬러유도선 | 입력툴상 컬러유도선 존재·색상·가능하면 개수 | 실제 노면의 컬러유도선 존재·색상·개수 |

시안색의 **진입 선형**과 시안색 **가로 정지선**은 모양·방향·위치로 구분해야 하며, 색상만 같다고 동일 특징으로 판정하지 않는다. 가림·화면 해상도·도면 표현 방식이 불분명하면 `판단 보류`로 표시한다.

**정지선 비교는 별도로 PASS / FAIL / REVIEW를 저장한다.** 입력툴에서 **시안색 가로줄 유무**를 읽고, 로드뷰에서 **횡단보도(흰색·노란색 반복 표시)가 아닌 단독 흰색 실제 정지선 유무**를 읽는다. 두 값이 같으면 `PASS`, 다르면 `FAIL`; 로드뷰 노면표시가 흐리거나 횡단보도와 구분되지 않으면 `REVIEW`로 남겨 **사용자가 추가 확인**한다. 로드뷰 검출 threshold는 UI 및 로컬 설정으로 조절 가능하며, 실제 사진에 맞춰 현장 보정한다.

## 4. 진입 후 검수 항목

좌·직·우 각각 별도의 사진을 기반으로 다음을 비교한다.

| 항목 | 비교 기준 |
|---|---|
| 방향별 도로 존재 | 입력툴에 해당 진출 방향이 존재하는가 ↔ 실제 로드뷰에 대응 도로가 보이는가 |
| 방향별 차로 수 | 입력툴이 표시·제공하는 **해당 방향 차로 수** ↔ 로드뷰 차로 수 |
| 일반 유도선 | 일반 경로 유도선 존재·개수 ↔ 실제 일반 유도선 존재·개수 |
| 컬러유도선 | 컬러유도선 존재·색상·개수 ↔ 실제 컬러유도선 존재·색상·개수 |

차로 수 **0**은 해당 진출 도로가 없다는 정황이 충분히 확인된 경우에만 고려하고, 사진 누락·가림·인식 실패는 **`null`/알 수 없음**으로 보존한다. 좌·직·우 방향은 **도로가 없어도 사진을 찍어야 하며**, 존재 여부는 **입력툴 기대 경로와 로드뷰의 실제 도로·건물 영역**을 비교하여 후보 판단한다. 건물이 사진에 있다는 사실만으로 도로가 없다고 단정하지 않는다.

## 5. 사용자 흐름 — 구현된 기본 흐름

1. 사용자가 HD_3D Tool과 NLadybugSv를 열고 교차로를 선택한다.
2. map_validator UI에 검수 ID가 표시된다. 저장 경로는 기존 설정을 사용한다.
3. 사용자가 화면을 **진입 전** 위치로 맞춘 후 해당 촬영 버튼을 누른다.
4. 사용자가 **좌 → 직 → 우** 순서로 직접 시점을 이동한 뒤 **도로가 보이지 않거나 건물이 있는 방향까지 포함해 3개 방향 모두 촬영**한다.
5. UI는 각 단계별 `미촬영/촬영 완료/부분 실패`를 표시하고, 재촬영 시 이전 버전을 보존한다. **도로 없음은 촬영을 건너뛰는 단계 상태가 아니라 사진 분석에서 다루는 관측 결과**다.
6. **촬영본 분석**은 현재 검수 ID에 저장된 단계별 사진과 입력툴 정보를 대조한다. **분석 중에는 다시 촬영하거나 프로그램을 조작하지 않는다.**
7. 결과를 **진입 전 항목**과 **진입 후 좌/직/우 항목**으로 나누어 입력툴 기대값·로드뷰 관측값·일치 여부·판단 보류 사유를 표시한다.
8. 사용자가 사진과 비교 결과를 확인해 최종 검수한다. AI 분석 결과가 업무 프로그램을 자동 승인·수정하지 않는다.

## 6. 화면과 데이터 설계 원칙

- 기존 반투명 소형 제어창 스타일과 **별도 UI 폴더 구조**를 유지한다.
- 화면은 **대상 설정 → 4단계 촬영 → 단계별 진행 상태 → 분석/중지 → 검수 결과 → 작업 로그**의 흐름으로 정리한다.
- 촬영 시 입력툴과 로드뷰를 **WGC 단일 방식**으로 1장씩 저장한다. 검수 ID와 촬영 단계 코드가 파일명에 드러나야 한다.
- 분석은 원본 사진을 덮어쓰지 않고 **`staged_analysis.json` 및 `overlays/`**에 근거와 후보 결과를 분리한다. 기존 `result.json`, `analysis.json`은 이전 버전 호환 자료로 보존한다.
- 결과에는 **기대값/관측값/비교 상태/근거 이미지/신뢰도 또는 보류 사유**를 분리한다. 인식 실패를 거짓값이나 차로 수 0으로 바꾸지 않는다.
- 단계가 빠졌거나 한쪽 사진만 있으면 어떤 단계·파일이 부족한지 알려준다. 나머지 촬영본의 부분 분석은 허용하되 전체 검수 완료로 취급하지 않는다. **없는 도로도 촬영한 이미지 자체를 증거로 사용한다.**
- 동일 단계 재촬영 시 원본 보존·교체 확인 등 안전한 처리 방식을 디자인 문서에 명시한다.
- 선택 ID 저장 규칙, 개인정보·실무 이미지 Git 제외, 로그, 사람이 최종 판단하는 원칙은 유지한다.

## 7. 교차로 방향별 스코어 데이터 축적

향후 여러 교차로를 통계적으로 비교하기 위해, **같은 검수 ID(Polygon ID - Link ID) 아래 총 6개의 로드뷰 도로 영역 스코어**를 저장한다.

| 촬영 단계 | 저장할 스코어 |
|---|---|
| 교차로 진입 전(`before`) | **좌측/직진/우측 스코어 3개** — 한 장의 사진을 좌·중앙·우 영역으로 나누어 계산 |
| 교차로 진입 후 · 좌(`after_left`) | **정면(직진) 스코어 1개** — 좌측 방향을 바라보고 촬영한 사진의 중앙 도로 영역 |
| 교차로 진입 후 · 직(`after_straight`) | **정면(직진) 스코어 1개** — 직진 방향 촬영 사진의 중앙 도로 영역 |
| 교차로 진입 후 · 우(`after_right`) | **정면(직진) 스코어 1개** — 우측 방향 촬영 사진의 중앙 도로 영역 |

모든 값은 **같은 도로 분할 모델에서 얻은 ROI 내 도로 픽셀 비율(0~1)**로 계산한다. 스코어가 높다는 뜻은 해당 *화면 영역*에 도로로 판독된 픽셀이 많다는 것이지, 회전 가능 여부나 실제 도로 존재 확률을 뜻하지 않는다. 사진 누락 시 스코어는 `null`/CSV 공란으로 기록하고 **0으로 대체하지 않는다**.

저장 구조는 **검수 ID별 `road_scores.json` + 재분석 시각별 `score_history/` 원본 이력 + 저장 상위 폴더의 전체 검수 ID 통합 `road_scores.csv`**로 구성한다. 진입 전/후 좌·직·우 짝별 **스코어 차이(후-전)**도 저장하지만 촬영 시점과 원근이 다르므로 **차이만으로 불일치를 확정하지 않는다**. 모델·ROI·원본 버전·계산 시각을 기록하여 이후 분석 기준 변경에도 비교할 수 있게 한다.

**현장 테스트에서 점수 판정 규칙이나 시야 기준이 달라지면 이 컨셉과 요구사항, 디자인 문서 및 스코어 버전 정책을 함께 갱신한다.**

| 업무 조작 | UI 촬영 및 분석에서 창 이동·Zoom·자동 로드뷰 조작 없음 | 유지 |

**사용자가 네 단계를 하나씩 촬영·검수하면서 발견한 새로운 요구사항은 계속 추가한다.** 요구사항은 [REQUIREMENTS.md](REQUIREMENTS.md)에, 컨셉에 해당하는 사항은 **이 문서에도 함께** 반영한다. 구현했다고 모든 기능의 정확도가 검증된 것은 아니다.

## 9. 성공 기준과 제약

- 사용자가 **네 단계 각각의 촬영**을 직접 수행하고 같은 검수 ID로 관리할 수 있다.
- 진입 전 **정지선/차로 수/화살표/컬러유도선**, 진입 후 **방향별 도로 유무/차로 수/일반 유도선/컬러유도선**의 비교 결과를 검토할 수 있다.
- 실제 입력툴에서 판독한 값과 로드뷰에서 관찰한 값을 **서로 다른 출처로 표시**한다.
- 불확실·누락·건물 등 비도로 관측·방향 도로 없음 후보·실제 불일치 의심을 각각 구별하며, 자동 판정으로 승인하지 않는다.
- HD_3D Tool의 3D 화면이 캡처로 흰색이 되지 않도록, `PrintWindow`는 사용하지 않고 창을 조작하지 않는다.

**중요:** 스크린샷만으로 정확한 지도–카메라 3D 좌표 정합, 차로 연결의 법적·공간적 확정 판정은 할 수 없다. 화면 표현·촬영 위치 차이, 가림, 차선 소실, 야간·마모 등의 영향은 검수자가 확인한다.

### 결과 화면 표시 보완

입력툴의 방향별 도로 존재 후보를 표시하고, 각 방향의 입력툴·로드뷰 도로 존재 비교를 P(일치 후보), F(불일치 의심), N(판단 보류)으로 표시한다. 이는 도로 형상 자체의 일치를 확인한 결과는 아니다. 진입 후의 도로 존재는 각 촬영 사진의 전방 중앙을 독립적으로 판단하고, 진입 전후 점수 차이는 화면에 표시하지 않는다. 기존 점수 파일의 차이 필드는 호환성을 위해 유지한다.

- RGB는 WGC 원본 OpenCV BGR에서 정확히 변환하며 초기 허용 오차는 **채널당 0**이다. 외곽선 RGB(0,0,255) 픽셀은 검출 마스크에서만 제외하고 원본 및 기존 PNG는 보존한다. 시안 정지선은 기존 HSV 넓은 범위 대신 설정된 RGB 색상만 사용한다.
- 파랑 U 및 연파랑 P 후보는 **8방향 연결 요소 + 3x3 작은 공백 연결**, 최소 픽셀 18·최소 외곽 장변 18px로 1차 분류한다. 곡선 형태와 다중 선들을 하나의 직선으로 오인하지 않으며 색상별로 독립 처리한다. U/P가 동일 색상 다른 오브젝트와 연결되면 오탐 가능성이 있으므로 검수 후보로만 취급한다.
- **검수 위치 영역과 후보:** `STOP ROI`(주황)은 S/G·C·A·W 공유, `GUIDE ROI`(자주)는 U 후보, `PATH ROI`(연한 파랑)는 P 후보 전용이다. U와 P ROI는 차량 현재 위치를 기준으로 별도 계산하며 **HDL View 글자 하단 이하의 유효한 도면 분석 범위**를 넘지 않는다. ROI 3종 테두리와 번호별 후보점을 근거 이미지에 마지막으로 표시한다. `review_regions` JSON에는 각 오브젝트의 검사 ROI와 후보 수를 기록한다.
- S는 Hough 선분 중점, G는 그룹 중점, C/A/W 기존 포인트, U/P는 연결 집합 대표점과 외곽 박스가 결과에 포함된다. `checks.approach_paths`와 `checks.guidance_lines`는 색상·연결·ROI·좌표·픽셀 수를 저장하며 이전 개별 촬영 JSON은 UI에서 선택적으로 읽는다.
- 현장 검증 전에는 RGB 정확값 외곽의 안티앨리어싱 픽셀 누락·교차로 외곽선과 겹친 가는 선 손실 가능성이 있다. 사람 검수 이후 허용 오차나 연결 조건을 조정해야 한다. Windows 실행 테스트·테스트 코드는 별도 요청이 없어 수행하지 않았다.

## 2026-11-17 현장 피드백: GUIDE ROI 차량 위치 기준 상향 배치

- 검수 이미지에서 GUIDE ROI가 지나치게 넓고 **HDL View 글자 하단(Y)부터 아래쪽까지** 이어져 차량 앞쪽 유도선 위치를 충분히 포함하지 못했다. 검수자가 분홍색으로 표시한 형태처럼 **현재 위치 빨간 사각형을 아래쪽 기준점**으로 삼고, 도면 위쪽으로 긴 세로 ROI를 배치한다.
- GUIDE ROI는 빨간 현재 위치 `point`와 검은 도면 경계 `canvas_bounds`로 독립 계산한다. **좌우 반폭 도면 너비의 18%(최소 55px), 위쪽 도면 높이 65%(최소 45px), 아래쪽 4%(최소 16px)**이며 도면 경계에 맞춰 자른다. 현재 위치가 유효하지 않으면 임의의 영역을 만들지 않는다. 빨간 현재 위치 표시점 주변의 상단 도면까지 포함할 수 있고, **STOP ROI의 상단 및 HDL View 글자 하단으로 GUIDE ROI 상단을 제한하지 않는다.**
- `GUIDE ROI` 자주색 테두리, U# 후보·원본 RGB(0,128,255)·8연결 그룹화는 유지한다. 결과 `checks.guidance_lines.roi`와 `roi_rules.positioning=vehicle_position_to_canvas_top`, `position_point_px`, `canvas_bounds`에 계산 기준을 기록한다.
- `STOP ROI`의 S/G/C/A/W와 `PATH ROI`의 P#는 **이번 변경에서 범위·기준을 수정하지 않는다**. WGC 수동 촬영 및 기존 원본 PNG·JSON 이력은 보존한다. Windows 실환경에서 ROI 크기/유도선 포함률은 별도 현장 확인이 필요하며 테스트 코드는 추가·실행하지 않았다.

## 2026-11-17 STOP ROI 축소 및 노면화살표 검출 범위 동일화

- 빨간 차량 현재 위치 `point`와 실제 검은 도면 `canvas_bounds` 기준으로 `STOP ROI`를 작게 계산한다. 좌우 반폭 도면 너비의 **18%**(최소 55px), 위쪽 도면 높이의 **25%**(최소 45px), 아래쪽 도면 높이의 **10%**(최소 35px). `blue_markings.stop_roi`에서 조정할 수 있으며 도면 경계를 넘지 않는다.
- **정지선 S#/G#와 노면화살표 A#는 같은 `checks.stop_line.roi` 좌표를 공유**한다. 기존 `local_road_arrow_candidates(..., roi=stop_line.get("roi"))`를 유지하여 화살표가 작은 STOP ROI 밖에서 검출되지 않도록 했다. 화살표 색상·회색 사각형·초록 테두리·흰색 제외 로직은 수정하지 않았다.
- 이전 넓은 검출 영역(HDL View/Input 글자 하단+10px 상단, 좌우 이미지 너비 31%, 현재위치 아래 이미지 높이 44%)은 `checks.stop_line.context_roi`로 분리했다. **중앙선 C, 흰선 W, 진입 경로선 P**는 이 넓은 영역을 계속 사용한다. GUIDE ROI(U)는 독립적으로 위쪽 탐색을 계속한다. 텍스트 기준이 확인되지 않으면 LINE 및 P 분석만 보류하고, STOP·A는 빨간 차량 위치가 검출되면 수행한다.
- 근거 이미지에 작은 주황색 `STOP ROI`(S/G·A)와 옅은 회색 `LINE ROI`(C/W/P) 테두리를 각각 표시한다. `review_regions`도 실제 분석 범위와 일치시킨다. 기존 WGC 원본·촬영 이력은 보존하고 새 분석 결과만 갱신한다.
- **현장 미검증:** 차량 위치가 교차로에 가까운 정도에 따라 STOP/A 후보가 작은 범위에서 누락될 수 있다. Windows 현장 분석과 자동 테스트는 요청받지 않아 실행하지 않았다.

## 2026-11-17 GUIDE/STOP/PATH ROI 위치 재설정 · LINE ROI 제거

- GUIDE ROI: 빨간 현재 위치 위쪽 교차로를 탐색하되, **차량 앞쪽 가장 가까운 시안색 정지선 후보 선분 위치까지 하단을 내린다**(4px 여유). 선분이 발견되지 않으면 현재 위치를 임시 기준으로 사용하고 `stop_line_reference.status`에서 `cyan_segment_candidate`와 `vehicle_position_fallback`을 구분한다. 시안색 후보는 실제 정지선으로 자동 확정하지 않는다.
- STOP ROI: **GUIDE ROI의 상단부터 전체 높이 70% 지점**까지 상단을 올리고, 하단은 현재 위치 아래 기존 10%를 유지한다. 정지선 S/G와 화살표 A는 같은 STOP ROI를 공유한다.
- PATH ROI: 현재 위치 빨간 마커를 아래쪽 기준점으로 삼아 **도면 높이 45% 위쪽**을 탐색한다. 마커 아래로는 4px 여유만 두며 도면 경계 밖으로 확장하지 않는다.
- **LINE ROI 삭제:** 회색 사각형과 'LINE ROI' 라벨, 별도의 context_roi 결과 및 UI 안내를 제거한다. 중앙선 C와 흰선 W는 세 ROI를 포함하는 내부 직사각형 탐색 범위(`candidate_search_bounds`)에서 계속 검출하되 **네 번째 테두리를 그리지 않는다**. C/W의 `review_regions.border`는 `none`이다.
- `blue_markings.guidance_roi/stop_roi/approach_roi` 수치를 갱신했고 ROI 3종(자주/주황/연파랑)은 유지한다. 기존 WGC 원본·검수 이력 보존. Windows 실환경 및 자동 테스트는 요청받지 않아 실행하지 않았다.
