# 프로젝트 컨셉 — map_validator

> 상태: **차기 검수 흐름 설계 확정안 / 단계별 구현 예정**  
> 기준: 2026-11-04  
> 관련 문서: [교차로 4단계 촬영·검수 UI 디자인](INTERSECTION_REVIEW_DESIGN.md), [기존 선형 후보 비교](LINE_GEOMETRY.md), [요구사항](REQUIREMENTS.md)

## 1. 목적

**map_validator**는 Windows의 **HD_3D Tool(입력툴)**에 등록된 교차로 도로 정보와 **NLadybugSv(로드뷰)**에서 실제 보이는 도로 표시가 일치하는지 검수하도록 돕는 로컬 데스크톱 도구다.

검수자가 교차로와 촬영 위치·시점을 직접 결정하고, 프로그램은 해당 검수 ID의 **입력툴 화면과 로드뷰 화면을 함께 캡처·보관**한다. 이후 사진에서 도로 표지·차로·선형을 인식해 항목별 차이를 표시한다. **자동 판정은 검수 보조 수단이며 최종 결정과 업무 프로그램의 실제 데이터 수정은 사용자 책임**이다.

핵심은 단순히 좌회전·우회전 도로 후보를 찾는 것이 아니라 **입력툴이 제공하는 교차로 진입 전·후 정보와 로드뷰에서 관찰되는 실제 정보를 같은 단계·같은 항목끼리 비교**하는 것이다.

## 2. 검수 단위

- 검수 ID: 기존 교차로 선형 검수 UI에서 선택된 **Polygon ID - Link ID** 기반. Polygon만 선택되면 Polygon ID만 사용한다.
- 검수 데이터는 `output.directory/<검수 ID>/` 아래 보관한다.
- 현재 선택 ID는 UI 메모리에서 갱신한다. **`config.yaml`에 선택 Polygon/Link ID를 저장하지 않는다.**
- 촬영 단위: **단계(stage) × 입력툴/로드뷰 한 쌍의 스크린샷**.
- 검수 단계는 네 종류이며 기본 표시 순서는 **진입 전 → 진입 후 좌 → 진입 후 직 → 진입 후 우**다.

| 단계 코드 | UI 표시 | 사용자가 촬영하는 내용 |
|---|---|---|
| `before` | 교차로 진입 전 | 진입 전 차로·정지선·화살표·컬러유도선이 보이는 시점 |
| `after_left` | 진입 후 · 좌 | 좌측 진행 방향의 실제 도로와 연결 차로가 보이는 시점 |
| `after_straight` | 진입 후 · 직 | 직진 방향의 실제 도로와 연결 차로가 보이는 시점 |
| `after_right` | 진입 후 · 우 | 우측 진행 방향의 실제 도로와 연결 차로가 보이는 시점 |

**촬영 시점·이동·각도 조정은 전적으로 사용자가 수행한다.** 검수 프로그램은 촬영 버튼을 눌렀을 때 현재 열린 두 창을 그대로 WGC(Windows Graphics Capture)로 캡처한다. 자동 W/S 이동, 화면 회전, Zoom 설정, 창 크기·위치 변경 및 자동 복원은 촬영 흐름에 포함하지 않는다.

**방향별 도로가 없어도 좌·직·우 3개 방향 모두 사용자가 반드시 촬영한다.** 프로그램은 로드뷰 사진에서 도로 영역과 건물 등 비도로 영역을 분석해, 입력툴상 예상 진출 도로와 비교한다. 기대 도로가 있는데 실제 촬영 방향이 건물 등으로 막혀 있는 정황이면 **불일치 의심**을 표시한다. 미촬영·사진 불명확·실제 도로 없음은 각각 별개로 처리하며, 자동 판단은 현장 테스트에 따라 지속적으로 보정한다.

## 3. 진입 전 검수 항목

| 항목 | 입력툴의 기대 정보 | 로드뷰에서 확인할 정보 |
|---|---|---|
| 정지선 유무 | 입력툴 화면의 **시안색 가로선**을 정지선 후보로 인식 | 실제 노면 정지선 존재 여부 |
| 진입 전 차로 수 | 입력툴이 나타내는 진입 차로 수 | 실제 진입 차로 수 |
| 차로별 방향 화살표 | 좌·직·우 및 조합 표시(좌직·직우 등) | 실제 노면 화살표의 위치·방향·조합 |
| 컬러유도선 | 입력툴상 컬러유도선 존재·색상·가능하면 개수 | 실제 노면의 컬러유도선 존재·색상·개수 |

시안색의 **진입 선형**과 시안색 **가로 정지선**은 모양·방향·위치로 구분해야 하며, 색상만 같다고 동일 특징으로 판정하지 않는다. 가림·화면 해상도·도면 표현 방식이 불분명하면 `판단 보류`로 표시한다.

## 4. 진입 후 검수 항목

좌·직·우 각각 별도의 사진을 기반으로 다음을 비교한다.

| 항목 | 비교 기준 |
|---|---|
| 방향별 도로 존재 | 입력툴에 해당 진출 방향이 존재하는가 ↔ 실제 로드뷰에 대응 도로가 보이는가 |
| 방향별 차로 수 | 입력툴이 표시·제공하는 **해당 방향 차로 수** ↔ 로드뷰 차로 수 |
| 일반 유도선 | 일반 경로 유도선 존재·개수 ↔ 실제 일반 유도선 존재·개수 |
| 컬러유도선 | 컬러유도선 존재·색상·개수 ↔ 실제 컬러유도선 존재·색상·개수 |

차로 수 **0**은 해당 진출 도로가 없다는 정황이 충분히 확인된 경우에만 고려하고, 사진 누락·가림·인식 실패는 **`null`/알 수 없음**으로 보존한다. 좌·직·우 방향은 **도로가 없어도 사진을 찍어야 하며**, 존재 여부는 **입력툴 기대 경로와 로드뷰의 실제 도로·건물 영역**을 비교하여 후보 판단한다. 건물이 사진에 있다는 사실만으로 도로가 없다고 단정하지 않는다.

## 5. 사용자 흐름 — 차기 목표

1. 사용자가 HD_3D Tool과 NLadybugSv를 열고 교차로를 선택한다.
2. map_validator UI에 검수 ID가 표시된다. 저장 경로는 기존 설정을 사용한다.
3. 사용자가 화면을 **진입 전** 위치로 맞춘 후 해당 촬영 버튼을 누른다.
4. 사용자가 **좌 → 직 → 우** 순서로 직접 시점을 이동한 뒤 **도로가 보이지 않거나 건물이 있는 방향까지 포함해 3개 방향 모두 촬영**한다.
5. UI는 각 단계별 `미촬영/촬영 완료/부분 실패/재촬영 필요` 상태를 보여준다. **도로 없음은 촬영을 건너뛰는 단계 상태가 아니라 사진 분석에서 다루는 관측 결과**다.
6. **촬영본 분석**은 현재 검수 ID에 저장된 단계별 사진과 입력툴 정보를 대조한다. **분석 중에는 다시 촬영하거나 프로그램을 조작하지 않는다.**
7. 결과를 **진입 전 항목**과 **진입 후 좌/직/우 항목**으로 나누어 입력툴 기대값·로드뷰 관측값·일치 여부·판단 보류 사유를 표시한다.
8. 사용자가 사진과 비교 결과를 확인해 최종 검수한다. AI 분석 결과가 업무 프로그램을 자동 승인·수정하지 않는다.

## 6. 화면과 데이터 설계 원칙

- 기존 반투명 소형 제어창 스타일과 **별도 UI 폴더 구조**를 유지한다.
- 화면은 **대상 설정 → 4단계 촬영 → 단계별 진행 상태 → 분석/중지 → 검수 결과 → 작업 로그**의 흐름으로 정리한다.
- 촬영 시 입력툴과 로드뷰를 **WGC 단일 방식**으로 1장씩 저장한다. 검수 ID와 촬영 단계 코드가 파일명에 드러나야 한다.
- 분석은 원본 사진을 덮어쓰지 않고 `analysis.json`과 시각적 근거 표시용 이미지로 분리한다.
- 결과에는 **기대값/관측값/비교 상태/근거 이미지/신뢰도 또는 보류 사유**를 분리한다. 인식 실패를 거짓값이나 차로 수 0으로 바꾸지 않는다.
- 단계가 빠졌거나 한쪽 사진만 있으면 어떤 단계·파일이 부족한지 알려준다. 나머지 촬영본의 부분 분석은 허용하되 전체 검수 완료로 취급하지 않는다. **없는 도로도 촬영한 이미지 자체를 증거로 사용한다.**
- 동일 단계 재촬영 시 원본 보존·교체 확인 등 안전한 처리 방식을 디자인 문서에 명시한다.
- 선택 ID 저장 규칙, 개인정보·실무 이미지 Git 제외, 로그, 사람이 최종 판단하는 원칙은 유지한다.

## 7. 현재 구현과 차기 구현 구분

| 영역 | 현재 저장소 상태(2026-11-04 기준) | 차기 목표 |
|---|---|---|
| 검수 ID | 교차로 클릭 후 Polygon/Link ID 갱신 | 유지 |
| 촬영 | 현재 두 창의 WGC 캡처 1회 | **4개 단계별 사용자가 촬영**, 단계 상태·재촬영 관리 |
| 비교 | 저장된 사진에서 색상 선형·로드뷰 도로 방향의 **후보** 비교 | 정지선, 차로 수, 차로 화살표, 일반·컬러유도선, 방향별 도로 유무 비교 |
| 결과 | 기존 `result.json`, `analysis.json`, 오버레이 | 단계별 기대값/관측값/불일치/보류 근거를 구조화 |
| 자동 조작 | UI 캡처·사진 분석에서 창 이동·Zoom 조작 없음 | 그대로 유지, **촬영은 항상 사용자 수동 위치 지정** |

**현장 테스트를 한 단계씩 진행하면서 발견한 판정 기준과 새 요구사항은 수시로 갱신한다.** 그 변경이 컨셉에 해당하면 이 문서에도 반드시 반영한다. 현재 기준은 방향별 촬영이 필수이고 건물/비도로 영역은 불일치 판단의 근거로 고려하되, 확정적인 오판을 피하기 위해 근거 부족 시 보류한다.

이 문서는 **제품 컨셉 및 목표 동작**을 설명한다. 표의 오른쪽 기능이 이미 구현되었다는 뜻은 아니다. 테스트 과정에서 추가·변경되는 구체적 검수 규칙은 [요구사항](REQUIREMENTS.md)에 순차 반영하고, UI·데이터 형식에 영향을 미치면 [디자인 문서](INTERSECTION_REVIEW_DESIGN.md)도 함께 갱신한다.

## 8. 성공 기준과 제약

- 사용자가 **네 단계 각각의 촬영**을 직접 수행하고 같은 검수 ID로 관리할 수 있다.
- 진입 전 **정지선/차로 수/화살표/컬러유도선**, 진입 후 **방향별 도로 유무/차로 수/일반 유도선/컬러유도선**의 비교 결과를 검토할 수 있다.
- 실제 입력툴에서 판독한 값과 로드뷰에서 관찰한 값을 **서로 다른 출처로 표시**한다.
- 불확실·누락·건물 등 비도로 관측·방향 도로 없음 후보·실제 불일치 의심을 각각 구별하며, 자동 판정으로 승인하지 않는다.
- HD_3D Tool의 3D 화면이 캡처로 흰색이 되지 않도록, `PrintWindow`는 사용하지 않고 창을 조작하지 않는다.

**중요:** 스크린샷만으로 정확한 지도–카메라 3D 좌표 정합, 차로 연결의 법적·공간적 확정 판정은 할 수 없다. 화면 표현·촬영 위치 차이, 가림, 차선 소실, 야간·마모 등의 영향은 검수자가 확인한다.
